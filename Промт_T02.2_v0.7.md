КОНТЕКСТ (уже принятые решения, которые нужно отразить)
- Режим «Мой клиент» (выбор внешнего клиента из базы) на платформе пока отсутствует и реализуется отдельной задачей после основных задач по избранным маршрутам. До его появления данные гостя вводятся вручную на экране заказа.
- Данные гостя передаются в существующих полях заявки «Дополнительное контактное лицо» (information.addContactFIO, information.addContactPhone) и в комментарии водителю (commentForDriver). Эти поля уже доходят до диспетчера и водителя.
- Для заявок по избранному маршруту в T04.1 не выполняются: флаг ожидания такси, лимит многоточечных поездок, запрет на пересечение заявок одного пассажира. В T04.1 сервис заявок сохраняет блок information и для такси.
- Цель поездки работает штатно: справочник целей организации, подстановка частой цели пользователя, штатные ограничения цели по дате, времени и дням недели.

ИЗМЕНЕНИЯ

1. Пассажиры: режимы штатного блока
Где: 1.1 (абзац о пользовательском вводе), 2.1 (шаг 4), 5.3 (абзац о режимах), AC-T02.2-33.
Что: вместо обязательного перечня «Я / Мой коллега / Мой клиент» написать: «Доступны режимы штатного блока «Кто пассажир?». Режим «Мой клиент» становится доступен на экране вместе с его появлением в штатном блоке и в T02.2 не разрабатывается». AC-T02.2-33: «Оформить заказ в каждом режиме штатного блока «Кто пассажир?». Все режимы доступны; правила фиксированной цены одинаковы».
Почему: режима «Мой клиент» на платформе нет, он делается отдельной задачей. Критерий приёмки T02.2 не должен зависеть от чужой доработки.

2. Данные гостя (новый подраздел в 5.3 «Данные гостя»)
Что:
- Блок необязателен. Если гость указан, ФИО обязательно; телефон необязателен (формат +7).
- TAXI: количество пассажиров от 1 до 4; для каждого гостя — ФИО одной строкой; для первого гостя — телефон.
- GROUP_TRANSFER, включая TRANSFER_CAR_CHOICE: количество пассажиров; ФИО пассажира и телефон — один контакт.
- Маппинг: ФИО первого гостя → information.addContactFIO; телефон → information.addContactPhone; количество → passengerCount. Остальные гости TAXI добавляются в commentForDriver строкой «Пассажиры: ФИО2; ФИО3; ФИО4». Если комментарий пользователя заполнен, строка с гостями добавляется перед ним, с новой строки; если пуст — в commentForDriver передаётся только строка с гостями.
- Это временное решение до появления режима «Мой клиент»; затем ФИО выбирается из базы клиентов.
Почему: к выпуску избранных маршрутов нужно заказывать поездки на гостей; существующие поля контактного лица уже отображаются диспетчеру и водителю, поэтому диспетчерская и приложение водителя не дорабатываются.

4. Правила изменений (6.6)

Почему: гость не влияет на цену и проверку маршрута.

5. Исключения проверок (3.4 и 6.2, строка «Проверки в T02.3 / T04.1»; AC-T02.2-35)
Что: к исключениям добавить запрет на пересечение заявок одного пассажира: «Для заявок по ИМ не выполняются проверка ожидания такси, лимит многоточечных поездок и запрет на пересечение заявок одного пассажира». В AC-T02.2-35 добавить проверку: две заявки TAXI по ИМ на одно время на одного пассажира создаются.
Почему: сотрудник оформляет несколько машин на одно время для разных гостей, а пассажиром заявки остаётся он сам.

6. Цель поездки (5.3, строка «Цель поездки и комментарий к цели»; AC-T02.2-11)
Что: «Цель выбирается из штатного справочника целей организации, доступных сотруднику. Штатно подставляется наиболее частая цель пользователя; ограничения цели по дате, времени и дням недели действуют как в обычной форме. Цель обязательна; из маршрута не заполняется». AC-T02.2-11: «Открыть экран. Дата и время пусты и не подставлены из карточки; цель штатно предзаполнена частой целью пользователя или пуста, если её нет. Без цели «Заказать» неактивна; без полного момента availability не вызывается. «Как можно скорее» и «Поездка в личных целях» отсутствуют».
Почему: цель обязательна для создания заявки; экран переиспользует штатный блок цели.

7. Часовой пояс (2.1 шаг 4, 5.3 абзац о поясе, 6.7)
Что: «Пояс пользователя — пояс устройства (браузера), как в штатной форме. Рядом с полем даты и времени показывается подпись пояса, например «по вашему времени, GMT+03». Сервер проверяет дневное и ночное окно по поясу первой точки».
Почему: сотрудник из другого пояса может ввести время подачи по местному времени Манжерока и заказать машину на другое время.

8. Смена версии (6.5)
Что: дописать «Заявка отправляется только после нового нажатия «Заказать» пользователем. Если в новой версии изменились вид, класс или автомобиль, экран сбрасывает зависящие от них поля (блоки полей вида, интервал аренды, данные гостя при смене вида) и повторяет их валидацию; для TRANSFER_CAR_CHOICE заново проверяется занятость машины».
Почему: после 409 пользователь должен увидеть новую цену и данные до отправки.

9. Повторная проверка при «Заказать» (6.2, 6.7)
Что: «При нажатии «Заказать» экран повторяет availability для текущей пары id/version и момента. При 409 — §6.5, при available=false — показ причины, заявка не отправляется. Изменение маршрута после этой проверки и до создания заявки не отслеживается: заявка создаётся по проверенной версии и её fixedCost».
Почему: между проверкой и созданием заявки маршрут могут изменить или деактивировать.

Почему: без segments и outcomeTariffId заявка не создаётся; пользователь должен понимать причину.

11. Связь с БТ (1.1, 6.6)
Что: «Экран использует методы T01.2 (GET карточки, availability) вместо prepopulate из БТ. Точки на экране только для чтения, поэтому правило БТ о переходе на динамический расчёт при изменении точек к экрану заказа по ИМ не применяется. Для другого маршрута пользователь оформляет обычный заказ. Переход на динамический расчёт при изменении созданной заявки — T04.2».
Почему: снимает противоречие с правилом БТ о динамическом расчёте.
