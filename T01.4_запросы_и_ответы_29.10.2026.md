# T01.4: запросы и ответы зависимостей

29.10.2026 · задача 4 «Интеграция с тарифным сервисом и получение стоимости» · к T01.2 от 29.10.2026 · основание — исходный код платформы; сервисы и стенд не запускались.

**Метки.** **[Код]** — поля, форматы и поведение взяты из исходников. **[Локально]** — пример проверен на настоящих классах tariff вне репозитория. **[Решение]** — предлагаемый способ реализации в T01.4. **[Запросить]** — нужно подтвердить на стенде. Все UUID, названия и суммы в примерах условные; ключи, типы и единицы — по коду.

**Сокращения путей.** TF — `tariff-main/application/src/main/java`; GEO — `geo-main/application/src/main`; GZ — `geo-zones-main/application/src/main/java`; CTR — `contractor-main/application/src/main/java`; DSP — `dispatcher-main/application/src/main/java`.

## Общие правила вызовов

- **Адрес.** Через шлюз — `/api/tariffs/…`, `/api/geo/…`, `/api/geo-zones/…`, `/api/contractors/…`, префикс шлюз отрезает. Напрямую — как сервис заявок: базовый адрес сервиса из окружения и тот же путь без префикса.
- **Заголовки.** `Authorization: Bearer <JWT пользователя>` и `Content-Type: application/json`. Все вызовы T01.4 выполняются в запросе пользователя, сервисный токен не нужен.
- **Пустые поля.** tariff, geo и geo-zones не выводят ключи со значением `null` (`default-property-inclusion: non_null`). Отсутствующий ключ означает «нет значения».
- **Единицы.** Расстояние — км, время в HTTP-запросах и ответах — миллисекунды, деньги — копейки, даты тарифа и договора — строки `yyyy-MM-dd`.
- **Сотрудник.** tariff ищет инициатора в своей копии сотрудников: если его нет, `/search` и расчёт отвечают 404 с `entity.name = "Employee"`.

## 1. Порядок вызовов

| Шаг | Вызов | Когда | Что берём |
|---|---|---|---|
| 1 | geo-zones `POST /searchBranch` по адресу первой точки | когда T01.2 нужен контекст первой точки: создание, предрасчёт, изменение | ветка зон, пояс |
| 2 | geo `GET /address` по координатам первой точки и снова `searchBranch` по адресу геокодера | `verifyFirstPointTerritory = true` | сверка первой точки |
| 3 | geo `POST /route` | `GEOMETRY_AND_PRICE` | `rawDistanceKm`, `rawTravelMs` |
| 4 | tariff `POST /search` по зонам ветки, отдельно INCOME и TRANSITIONAL | предрасчёт | кандидаты |
| 5 | tariff `GET /taxi/{id}` или `GET /group_transfer/{id}` | каждый кандидат и выбранный тариф | реквизиты, класс, ночь, зоны, автомобили, коэффициенты |
| 6 | tariff `GET /contracts/{contractId}` | каждый кандидат и выбранный тариф | активность, организации, даты |
| 7 | contractor `GET /{contractorId}/transport/` | `TRANSFER_CAR_CHOICE` | автомобиль, `transportInfo` |
| 8 | tariff `POST /calculate/enum/{transportType}/{tariffId}` | цена точного варианта | `recommendedCost` |

Продление, `GET checkTariff` и availability выполняют шаги 5–6 без расчёта цены. В `PRICE_ONLY` шаги 2–3 не выполняются: цена считается от сохранённых метрик.

```json
200
[
  { "id": "22222222-0000-4000-8000-000000000001", "name": "Манжерок", "code": "MNZ", "parentId": "22222222-0000-4000-8000-000000000002", "timeZone": "Asia/Barnaul" },
```

**[Код]** geo вызывает 2ГИС `/3.0/items/geocode` с `type=building` и сортировкой по расстоянию (GEO `resources/application.yml:39-72`). Передавать только координаты: без координат и строки адреса geo сразу отвечает `200 []`, а при координатах вместе со строкой складывает результаты двух поисков.

| Ответ 2ГИС | Ответ geo | Для FavoriteRoute |
|---|---|---|
| Здания найдены | 200, список | сверка веток по `searchBranch` адреса геокодера |

Тело 417: `{"timestamp": "…", "path": "/address", "message": "<текст 2ГИС>"}`. По тексту причину не определять.

### 2.3. Маршрут — geo `POST /route`

**[Код]** geo строит маршрут попарно по соседним точкам и суммирует отрезки (GEO `RouteServiceImpl.java:48-90`). `distance` — км (`total_distance / 1000`), `time` — мс, ожидание в `time` не входит.

```json
  "coordinates": [
    { "latitude": 51.8213, "longitude": 85.8002 },
    { "latitude": 51.8335, "longitude": 85.7861 },
    { "latitude": 51.9940, "longitude": 85.9156 }

  "distanceUnit": "KILOMETERS",
  "routeType": "CAR"

```

```json
200
{
  "waypoints": [ { "latitude": 51.8213, "longitude": 85.8002 }, { "latitude": 51.8335, "longitude": 85.7861 }, { "latitude": 51.9940, "longitude": 85.9156 } ],
  "distance": 18.4,
  "time": 1560000,

    { "distance": 2.1, "time": 240000, "coordinates": [ { "latitude": 51.8213, "longitude": 85.8002 }, { "latitude": 51.8335, "longitude": 85.7861 } ] }
```

|---|---|

| `waitingTime` | `0`: ожидание есть только у промежуточных точек |

| `trafficJamScore` | `0`: надбавка за пробки в рекомендуемую цену не входит |
| `options` | не передавать: опции TAXI дают свои коэффициенты |
| `startPoint` | первая точка, как фронт |

- Сверить `id` ответа с запрошенным `tariffId`; расхождение — 502 `DEPENDENCY_INVALID_RESPONSE`.
- Сам расчёт проверяет только `active` тарифа: организацию, договор, период, класс и ночь FavoriteRoute проверяет по карточкам (2.5, 2.6).
- **[Код]** Расчёт делает и побочные обращения, которые могут уронить ответ с 500:
  - **Лимиты.** Вызывается gRPC limits `limitReservation` с `checkLimit = true`. Сотрудник без подразделения даёт `NullPointerException` (`:746`).
  - **Расходный тариф.** Для INCOME-тарифа TAXI нужен ровно один подходящий расходный тариф: та же зона и класс, не дороже доходного, перевозчик не ограничен для организации, класс разрешён должностью инициатора. Иначе 500 «Не найден расходный тариф» или «Должен быть только один найденный расходный тариф» (`:392-460`). Для TRANSITIONAL и GROUP_TRANSFER этот шаг тривиален.

  По T01.2 такие 500 — 502 `DEPENDENCY_ERROR`; это ошибки данных и настройки tariff, а не FavoriteRoute.

## 3. Ошибки зависимостей

| Ответ | Тело | Код T01.2 |
|---|---|---|
| 404 тарифа или сотрудника | `{"timestamp", "path", "entity": {"name": "BaseTariff", "TaxiTariff", "GroupTransferTariff" или "Employee", "id": …}, "message"}` | для выбранного тарифа — по правилам операции (непригоден); иначе 502 `DEPENDENCY_ERROR` |
| 400 валидации | `{"timestamp", "path", "message": "Bad Request", "problems": [{"field", "value", "constraints": [{"type", "value"}]}]}` | 502 `DEPENDENCY_INVALID_RESPONSE`: адаптер собрал неверный запрос |
| 417 geo | `{"timestamp", "path", "message"}` | 502 `DEPENDENCY_ERROR` |
| 500 | `{"timestamp", "status": 500, "message": "Request failed. Please contact support", "error", "path"}` | 502 `DEPENDENCY_ERROR` |
| 503, отказ соединения | — | 503 `DEPENDENCY_UNAVAILABLE` |
| Таймаут | — | 504 `DEPENDENCY_TIMEOUT` |
| 200 с неверным типом, единицами, отрицательной метрикой или чужим id | — | 502 `DEPENDENCY_INVALID_RESPONSE` |

Тела 404 и 400 — `ExceptionBody` из `transport_core` (`exceptions/dto/ExceptionBody.java`, пустые поля опускаются); тело 500 — `Map` из `RequestExceptionHandler.java:332-350`. 417 от tariff («не определены регион или пояс») возникает только на каталожных путях, которые FavoriteRoute не вызывает. 403 от проверки прав на путь — технический отказ, а не «тариф недоступен».

## 4. TAXI: выбор нейтрального момента

T01.2 требует цену TAXI с временным коэффициентом 1,0 в дневном или ночном окне маршрута, `calculationDate` — от `referenceDate` до `referenceDate + 6`. Коэффициент организации (`coefOrg`) сохраняется.

**[Код]** Временной коэффициент TAXI (`CalculateServiceImpl.java:991-1012`, `TimedTariffParams`), местное время берётся из `tripDate` и `timeZone`:

| День | Время | Коэффициент из `timedTariffParams` |
|---|---|---|
| Суббота, воскресенье | весь день | `coefDayOff` |
| Будни | 07:00–10:00 | `coefWorkDayMorning` |
| Будни | 10:00–18:00 | `coefWorkDayNoon` |
| Будни | 18:00–22:00 | `coefWorkDayEvening` |
| Будни | 22:00–07:00 | `coefWorkDayNight` |

Дневное окно маршрута по T01.2 — 06:00–22:00, но в будни 06:00–07:00 тариф считает по ночному коэффициенту. **[Локально]** При коэффициентах 1,2 / 1,0 / 1,3 / 1,5 / 1,1 пятница 10:00 даёт 1,0, 07:30 — 1,2, 06:30 — 1,5, суббота 12:00 — 1,1.

**[Решение]** Алгоритм для T01.4:

1. Взять `timedTariffParams` из карточки TAXI.
2. Для дат `referenceDate … referenceDate + 6` перебрать представительные моменты окна маршрута:
   - дневной маршрут — 06:30, 08:00, 12:00, 20:00;
   - ночной — 23:00 и 03:00.
3. Взять первый момент с коэффициентом ровно 1,0, если договор действует на эту дату.
4. Передать `tripDate` (эпоха в мс местного момента), `timeZone`, `trafficJamScore = 0`, без `options`.
5. Не нашлось — 503 `CALCULATION_MODE_UNAVAILABLE`.

`calculationDate` — местная дата выбранного момента. Надбавка за пробки нейтральна, только если `traffic.threshold ≥ 0` (по умолчанию 7) или `coefTraffic = 0`.

GROUP_TRANSFER: временного коэффициента нет, `calculationDate = referenceDate`.

## 6. Как снять реальные ответы со стенда

Примеры выше собраны по коду. Окончательный формат лучше зафиксировать ответами стенда — с JWT пользователя организации Манжерока:

```bash
curl -sS -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" -X POST "$GW/api/geo-zones/searchBranch" -d '{"country":"Россия","region":"Республика Алтай","city":"Манжерок"}'
```

```bash
curl -sS -H "Authorization: Bearer $JWT" "$GW/api/geo/address?latitude=51.8213&longitude=85.8002"
```

```bash
curl -sS -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" -X POST "$GW/api/tariffs/search?page=0&size=100" -d '{"transportType":"TAXI","serviceType":"EMPLOYEE_TRANSPORTATION","organizationId":"<UUID организации>","contractType":"INCOME","active":true}'
```

**[Запросить]** на стенде:
- ответ geo на точку без здания (поле, вода): 417 или `200 []`;
- реальные карточки TAXI и GROUP_TRANSFER, включая общий тариф без подразделения;
- `traffic.threshold` и `timedTariffParams` тарифов Манжерока;
- права EMPLOYEE, ADMIN и ENGINEER на пути 2.1–2.8.

## 7. Что пока не закрыто

- **Подтверждение доступа пользователя к конкретному тарифу.** Готового способа в существующих API нет, решение готовится в T01.2 и T01.4. До него собственные правила подразделения и должности не реализовывать (подробно — ответ разработчику, п. 2.2).
- **Распознаваемый ответ «у первой точки нет здания»** дописывается в T01.2 (2.2).
- **`transportServiceType` для `/route`** — зафиксировать один вариант (2.3).
