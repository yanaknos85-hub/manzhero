# Промпт для правки T01.2 «API справочника избранных маршрутов»

Ты системный аналитик проекта «Избранные маршруты» АС «СберТранспорт», Манжерок. Внеси правки в приложенный файл T01.2_FavoriteRoute (редакция от 30.10.2026).

Правила работы:
- Работай с этой редакцией. Сохрани структуру, оформление, нумерацию разделов и коды критериев.
- Меняй только места, перечисленные ниже. Контракт API, коды ошибок, DTO, алгоритм сверки первой точки и остальные критерии не меняй, новых требований не добавляй.
- Изменённые фрагменты выдели фиолетовым цветом.
- Источники решений — T01.3 «Ввод точек маршрута» (версия 11) и T01.4. В тексте документа ссылайся только на них.
- T01.4 в этом задании не правь.

Основание правок. В интерфейсе справочника (T01.3) карты нет: точка выбирается поиском адреса по строке (Geo GET /address, параметр location), координаты и адресные части берутся из выбранного варианта. Сообщение FavoriteRoute о неподтверждённом здании первой точки называет только причину, а что сделать, подсказывает экран у поля «Откуда». Экран различает подтверждённый отказ записи и неизвестный исход.

## 1. Метод геокодирования и источник координат

1.1. Раздел 5, «Точка маршрута» → «Нормализация и точность». Добавь в конец списка пункт:
«• Координаты и адресные части точки формирует интерфейс T01.3 из варианта, выбранного в поиске адреса. FavoriteRoute адреса в координаты не преобразует.»

1.2. «Geo и сверка первой точки» → «Контракт сверки», первый пункт.
Сейчас: «T01.4 сверяет первую точку тем же методом обратного геокодирования, что и T01.3: GET /address сервиса geo, через шлюз — GET /api/geo/address.»
Нужно: «T01.4 сверяет первую точку методом GET /address сервиса geo, через шлюз — GET /api/geo/address. T01.3 использует этот же метод для поиска адреса по строке.»
Остаток пункта («Передаются только latitude и longitude первой точки; …») не меняй.

1.3. AC-F-121, проверяемый результат.
Сейчас: «Сервер использует тот же метод обратного геокодирования, что T01.3, передавая только координаты.»
Нужно: «Сервер использует метод GET /address сервиса geo, передавая только координаты.»

1.4. AC-F-68, условие.
Сейчас: «Первая ручная точка у здания содержит регион и координаты…»
Нужно: «Первая точка у здания содержит регион и координаты…»
Слово «ручная» читается как ручной ввод координат, которого в T01.3 нет.

1.5. Проверки внешних контрактов, пункт «Проверить геокодер и regionBranch…».
Сейчас: «…одинаковый метод клиента и сервера, в geo передаются только координаты первой точки без строки адреса.»
Нужно: «…один метод GET /address у клиента (поиск по строке) и у сервера (по координатам); при сверке в geo передаются только координаты первой точки без строки адреса.»

Сейчас: «Для geo 200 []: «Не удалось подтвердить здание по координатам первой точки. Уточните точку на карте».»
Нужно: «Для geo 200 []: «Не удалось подтвердить здание по координатам первой точки».»

2.2. «Geo и сверка первой точки», пункт «При geo 200 [] создание, предварительный расчёт и изменение первой точки отклоняются без записи…».
Сейчас: «Пользователь получает message: «Не удалось подтвердить здание по координатам первой точки. Уточните точку на карте».»

После правки в документе не должно остаться формулировки «Уточните точку на карте» и других упоминаний карты как способа выбрать точку.

## 3. Неизвестный исход записи

3.1. Раздел 5, «Общие правила запросов и ответов» → «Размер и сохранение», пункт «Неизвестный исход записи уточняется чтением…».
Сейчас: «Неизвестный исход записи уточняется чтением; потеря ответа не доказывает rollback и не запускает слепой повтор POST.»
Нужно: «Неизвестный исход записи уточняется чтением; потеря ответа не доказывает rollback и не запускает слепой повтор POST и PUT. Исход неизвестен при потере ответа (сетевой сбой, таймаут ожидания на клиенте), при ответе 500 и при ответах 502, 503, 504 без прикладного code FavoriteRoute. Ответы 4xx и ответы 502, 503, 504 с прикладным code FavoriteRoute означают, что запись не выполнена: обращения к зависимостям завершаются до COMMIT.»

3.2. «Ошибки хранения и конкурентной записи», таблица. Добавь строку:
«Результат COMMIT неизвестен из-за потери соединения с базой | 500 | INTERNAL_ERROR; итог уточняется чтением.»
Строка должна быть согласована с пунктом «Если результат COMMIT неизвестен из-за потери связи…» под таблицей.

3.3. Раздел 7, «Правила вызова API». После пункта «Обрабатывать HTTP 401/403 независимо от наличия code; для CONCURRENT_OPERATION_BUSY учитывать Retry-After: 1» добавь пункт:
«• При неизвестном исходе POST и PUT (раздел 5, «Размер и сохранение») клиент уточняет итог чтением: после PUT — GET /api/favorite-routes/{id} и сверка с отправленными значениями по правилам нормализации, после POST — список маршрутов. Автоматически запись не повторяется. Ручной повтор PUT выполняется с исходной version; ответ 409 VERSION_CONFLICT обрабатывается по правилу выше.»
