# Технические проверки И1–И8: что уже есть со стенда

Вопросы взяты из раздела 8.2 «Технические проверки, которые выполняет команда». Ответы по коду подготовлены в соседней задаче и переданы 16.10.2026. Здесь собрано, какие пункты из «Остаётся» и из самих формулировок проверок закрывают наши наблюдения на тестовом стенде. Это наблюдения 08.10, 12.10 и 13.10.2026, собранные для T01.1. Подробности - в `НАХОДКИ_FavoriteRoute.md`, номер дополнения указан в скобках.

Условия наблюдения:
- Наблюдали экраны корпоративного и клиентского кабинетов и сетевые запросы браузера под одной тестовой организацией.
- Манжерока на стенде нет.
- Версия сборки стенда нигде не фиксировалась. По исходникам её не установить: архивы без `.git`, исходники шлюза датированы 2023 годом. Поэтому требование «с датой и версией стенда» выполнимо только по дате.
- Внутренние адреса стенда, номера автомобилей и персональные данные сюда не переносятся.

Обозначения: S1 в формулировках проверок - согласованная модель T01.1. Нумерация И - по разделу 8.2. Её не надо путать с И1 «Адрес для диспетчерской» в ответах архитектора от 15.10.

## И1. Шлюз, ExceptionBody, страница, `/allow`

**Есть со стенда.**
- Клиент обращается к сервисам через шлюз по образцу `/api/<ресурс>/...`. В запросах видны:
  - `POST /api/tariffs/search`, `POST /api/tariffs/calculate`;
  - `GET /api/geo/address?location=...` и `GET /api/geo/address?latitude=...&longitude=...`;
  - построение маршрута в geo;
  - `/api/organizations/self/addresses/favorite`.

  Это совпадает с образцом маршрутов шлюза из ответа по коду (дополнения 9, 16, 19; раздел A.3 «Версии и соответствие стенду»).
- Search отдаёт Spring Page: `content`, `pageable`, `totalElements`, `totalPages`, `number`, `size`, `first`, `last`. Нумерация страниц с нуля. Параметры страницы приходят и в строке запроса (`size=50&page=0`), и в теле (`page: {pageNumber, pageSize}`) (дополнение 9.7). Стенд показывает, что сервисы отдают на самом деле; рекомендация взять платформенный `Page` этим не опровергается.

**Нет со стенда:**
- версия и коммит;
- поведение пути коллекции без «/» на конце;
- реальное тело ExceptionBody: при 417 на обратном геокодировании фиксировалось только сообщение «address not found» в консоли клиента;
- доступ к `/allow`;
- диагностические поля `/calculate`.

## И2. Пользователь, контекст организации, digitId

**Есть со стенда.**
- Номера объектов тестовой организации содержат общую часть `0013`: тарифы TF-0013-…, пользователи US-0013-…, должности PS-0013-… Это подтверждает формат digitId - четыре цифры с ведущими нулями, `%04d` (дополнение 9.7).
- Должности организации с наборами классов такси, у части должностей список пуст (дополнение 9.4).

**Нет со стенда:**
- состав JWT - токен не разбирали;
- максимальный digit_id: видна только своя организация;
- цепочка «сотрудник - подразделение - организация» в данных;
- задержка доставки событий;
- тест «контекст ещё не готов».

## И3. Часовой пояс

**Есть со стенда.**
- Клиент передаёт `timeZone` в запросе расчёта (`POST /api/tariffs/calculate`). Значение не записывалось (дополнение 9.5).
- В справочнике есть зоны Республики Алтай: тарифы такси и группового трансфера тестовой организации заведены на эту зону (дополнение 9.2). Значение её часового пояса не проверялось.

**Нет со стенда:**
- выгрузка зон без пояса или с пустым поясом;
- пояс для ручных адресов;
- поведение при неизвестном поясе.

## И4. Тарифы и договоры

**Есть со стенда.**
- **Ответ search** (дополнение 9.5). Элемент содержит id, humanReadableId, region/regionId, transportType, serviceType, active, organizationId, contractId, contractNumber, contractorId, contractorName, isNightTariff. Класса, типа договора, признаков трансфера, цены и периода в ответе нет.
- **Даты договора** (дополнение 9.3):
  - в кабинете у договора есть «Действует с — по»;
  - три из шести договоров на 08.10 истекли по сроку, но остаются «Активный», и их тарифы активны в search;
  - территория договора трансфера не совпадает с регионами его тарифов.
- **Несколько тарифов одного класса** от разных договоров на одной зоне: Москва и МО, «Эконом» (дополнение 9.6).
- **Форма правки тарифа трансфера** (дополнение 22.3):
  - заблокированы услуга, вид транспорта, корпоративный клиент, контрагент и номер контракта;
  - доступны территория, период и цены, у «Эконом» и «Комфорт+» - класс;
  - поля подразделения в форме нет.
- **Форма договора** (дополнение 22.4): у трансфера редактируются территория и дата окончания, дата начала заблокирована; у такси период только для чтения.
- **Признак VIP** виден только у тарифа «Выбор автомобиля». Минимальная поездка: 100 км и 400 ₽ (Эконом), 50 км и 5 000 ₽ (Выбор автомобиля) (дополнение 22.3).
- **Коэффициенты времени** в проверенных карточках тарифов такси, в том числе по Республике Алтай, равны 1,00, в форме они недоступны (дополнения 9.5, 9.7 и снимок карточки от владелицы задачи). Значит, на стенде режим «без временных надбавок» сейчас ничем не отличается от обычного. Изменить коэффициенты может загрузка прайса.
- **Расчёт без geo.** Расчёт принимает distance и time готовыми: в запросе клиента они взяты из ответа geo (дополнение 9.5). Это подтверждает, что расчёт цены без вызова geo возможен.
- **Карточка автомобиля** в «Автосервисе» привязывает машину к организациям и подразделениям (дополнение 22.4).

**Нет со стенда:**
- тарифы с null в признаках трансфера;
- организация подразделения;
- частичный отказ списочного расчёта;
- автомобиль у нескольких перевозчиков;
- изменение тарифа во время расчёта;
- второй тариф трансфера с теми же параметрами.

## И5. Geo

**Есть со стенда.**
- **Единицы.** 08.10: distance в км с тремя знаками (2.343; 0.589), time в мс (380000; 118000). 13.10: маршрут по двум точкам - 17.016 км и 1 963 000 мс; время кратно 1000, то есть провайдер отдаёт целые секунды (дополнения 9.7, 22.1).
- **Нулевые участки.** У корректного маршрута первый и последний участки нулевые, у последнего пустой список координат (дополнение 23).
- **Исходные метрики.** Сумма distance участков в double даёт 17.016000000000002 (дополнение 22.1).
- **Ответы по вызовам.** Поиск строкой по несуществующему адресу - 200 и `[]`. Обратное геокодирование вне здания - 417 «address not found», клиент повторяет запрос трижды (дополнения 19, 22.2).
- **Адрес без частей.** В выдаче поиска есть объекты без country и region. У точки, выбранной по названию объекта, нет улицы и дома, строка адреса вырождается в «Москва, » (дополнения 16, 22.2).
- **Написания города.** В city встречаются «Московская область», «Москва город федерального значения», «Москаленский район» (дополнение 22.2).
- **building и structure** в ответах отсутствуют. Корпус и строение приходят внутри house: «15 к1», «вл7 ст9» (дополнение 22.1).
- **district** приходит у точек в областях (дополнение 22.2).
- **Точность координат.** До 14 знаков при клике по карте, до 6 из поиска (дополнение 22.1).

**Нет со стенда:**
- версия стенда;
- пустой маршрут от провайдера и частичный маршрут с ответом 500 (есть только по коду);
- 417 на построении маршрута;
- повтор при 502;
- адрес Манжерока: подстановка settlement в city;
- house, пришедший списком.

## И7. PostgreSQL

Со стенда нет ничего: версия СУБД стенда неизвестна, запроса `SELECT version()` не выполняли. Есть только локальные прогоны DDL вне стенда, это не целевая версия:
- PostgreSQL 16.13 в контейнере сессии: 22 случая, ограничения;
- PostgreSQL 18.6 через PGlite у владелицы задачи.

Конкурентность ни в одном из прогонов не проверялась.

## И8. Производительность

Замеров времени со стенда нет. Есть только наблюдения о числе вызовов:
- обратное геокодирование при 417 клиент повторяет трижды;
- search для тестовой организации вернул 17 активных тарифов на одной странице размером 50. Из них 10 тарифов такси и 3 трансфера, то есть до 13 расчётов на построение списка.

Время ответа при десятках вызовов, при 2 и 26 точках и для административного списка не измерялось.

## Уточнения по коду к ответам соседней задачи

Это не стенд, но меняет выводы:
- **Пояс в расчёте по tariffId (И3).** Расчёт по tariffId пояс региона сам не определяет: он берёт timeZone из запроса, а без него считает по GMT+03 (`CalculateServiceImpl.getTripTime`). Если FavoriteRoute не передаст пояс, временная полоса такси для региона с другим поясом определится по московскому времени. Это прямо касается запрета «нельзя подставлять UTC»: платформа подставит не UTC, а GMT+03.
- **Начальная загрузка (И2).** Кроме переотправки всех топиков в corporate есть gRPC `All`, `One`, `Refresh` (`organizations.proto`). Сервис согласований дочитывает организацию через `One`. В исходной конфигурации топики хранят сообщения 7 суток с политикой compact,delete (дополнение 22.5).
- **Машина и организация (И4).** Оба расчёта по автомобилям ищут тарифы только организации из запроса. Расчёт по одному автомобилю дополнительно требует, чтобы машина входила в transport_ids тарифа (`GroupTransferTariffRepository.findAllTariff`). Принадлежность машины организации этим проверяется, если организацию подставляет сервер.
- **Признаки трансфера (И4).** Через API признаки по умолчанию false (примитивы `NewGroupTransferTariffDTO`), кабинет отправляет их как false. Значения по умолчанию в базе нет. Поэтому null возможен только в старых данных или при прямой записи (дополнение 22.6).
- **Договор у тарифа (И4).** При сохранении через API договор обязателен у такси и трансфера (`TariffServiceImpl.save`). Ограничения NOT NULL на `tariff.contract_id` нет. NPE у трансфера без договора возможен только на старых данных.
- **Дедлайн всего запроса (И8).** У всех HTTP-запросов фронта таймаут 10 с (`mf-core HttpMiddleware.ts`). Расчёт маршрута из 26 точек (25 последовательных запросов к 2GIS, до 50 с повторами) должен уложиться в этот предел, иначе фронт оборвёт запрос раньше сервера.
- **Режим без надбавок (И4).** Формулировка «для такси это доработка тарифного сервиса в рамках T01.4» расходится с границей 08.10: T01.4 вызывает существующие методы и сервис тарифов не меняет. Кроме того:
  - базовой цены в ответе расчёта нет;
  - минимальные стоимости применяются до умножения на коэффициент;
  - округление до рубля - после умножения.
