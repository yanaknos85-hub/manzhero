# «Мой клиент»: контекст для разработки

Редакция 09.11.2026. Подготовлено аналитиком проекта «Избранные маршруты» (Манжерок) для команды ДЗО.

Документ собирает всё, что известно о режиме на сегодня: зачем он нужен, как платформа работает без него, где его придётся реализовывать и какие решения нужно принять. Разделы 1–3 — факты (встречи, ответы заказчика, стенд, код). Разделы 4–5 — предложения аналитика проекта, а не утверждённые решения: окончательные решения за командой ДЗО, архитектором и заказчиком.

## 1. Зачем нужен режим

**Бизнес-контекст.** Курорт «Манжерок» (ДЗО Сбера) заказывает через СберТранспорт такси и трансферы не только для сотрудников, но и для гостей: встреча в аэропорту, переезды между объектами курорта, экскурсии. Гость — не сотрудник организации, у него нет учётной записи и карточки в справочнике сотрудников.

**Связь с проектом «Избранные маршруты».** В рамках проекта сотрудник Манжерока заказывает поездку по заранее заведённому маршруту с фиксированной ценой. По решению заказчика заказ по избранному маршруту доступен в трёх режимах: на себя, на коллегу, на клиента. Режимы «на себя» и «на коллегу» на платформе есть, «на клиента» — нет. Экран заказа по избранному маршруту переиспользует штатный блок «Кто пассажир?», поэтому режим «Мой клиент» появится на нём, как только появится в штатном блоке. В задачи проекта «Избранные маршруты» режим не входит.

**Почему делает команда ДЗО.** Ответ заказчика (Инга, продуктовый владелец СберТранспорта), 09.11: «Сущность «Мой клиент» добавляет команда ДЗО, так как в банке данный функционал не нужен».

## 2. Требования, озвученные заказчиком

### 2.1 Встреча 02.09.2026 (утверждение дизайна)

Режим был представлен как новая сущность для Манжерока:

- **Список клиентов-физлиц в корпоративном кабинете** — рядом с сотрудниками («организация, структура, сотрудники и будет блок клиенты физлиц»). Список можно заполнить заранее, загрузив клиентов так же, как сотрудников.
- **Выбор при заказе.** В заказе появляется отдельный вариант «Мой клиент»: клиента выбирают из списка по ФИО, а если его нет — добавляют кнопкой «Добавить новый» прямо с экрана заказа.
- **Данные клиента:** фамилия, имя, отчество и номер телефона. Телефон необязателен («может быть ребёнок»). Телефон нужен, чтобы «привязать уведомления».
- **Несколько пассажиров:** «если нужен ещё один — кнопка добавить ещё одного».
- **Бюджет:** «Мой клиент не участвует в бюджете. Бюджет по нему не будет считаться».
- **«Мои заявки»** в клиентской части: заявки для коллег и заявки для клиента, с данными заказа (название маршрута, пассажир, стоимость).
- **Виды транспорта:** такси и трансфер.
- **На будущее:** заведение клиентов из CRM Манжерока в момент бронирования; обсуждение с Владимиром не завершено.

### 2.2 Ответ заказчика 09.11.2026

1. Сущность «Мой клиент» добавляет команда ДЗО: банку функционал не нужен.
2. В диспетчерской это поле «пассажир», статус пассажира (сотрудник или клиент) для неё неважен.
3. Функционал не может быть минимальным. Вариант «пассажир остаётся сотрудником, данные гостя записываются в заявку отдельными полями» отклонён: нужна полноценная сущность.

### 2.3 Дизайн-макеты

- **«Встреча гостя» (такси):** количество пассажиров от 1 до 4, для каждого — поле «Введите ФИО» с выпадающим списком и добавлением нового.
- **«Экскурсия»:** количество пассажиров, ФИО пассажира, телефон, дополнительные атрибуты, комментарий водителю.

Макеты — для экрана заказа по избранному маршруту, переключателя «Я / Мой коллега / Мой клиент» на них нет. Вариант с переключателем — на стандартном экране заказа, показанном на встрече.

## 3. Как платформа работает сейчас

Источники: тестовый стенд (проверка 06.11.2026) и доступный проекту снимок кода. Снимок старше встречи 02.09: миграции сервиса заявок — по 22.10.2025, сервиса corporate — по 28.10.2024, веб-клиент — 2024 год. Работу, начатую после этого, снимок не показывает.

### 3.1 Пассажир заявки — всегда сотрудник

| Где | Как устроено |
|---|---|
| Веб-форма заказа (client-passengers) | Блок «Кто пассажир?»: только «Я» (`me`) и «Мой коллега» (`notme`). «Мой коллега» — поиск по сотрудникам подразделений (`DepartmentEmployeeAutoComplete`). Файл `CreateTripRequest/Components/Additional/AdditionalPassenger.tsx`, одинаково в ветках main и develop. |
| Сервис заявок (passenger_request) | `NewRequestDTO.passenger` — обязательный `EmployeeDTO` (`@NotNull`). При создании такси и трансфера сервис ищет пассажира в своей копии справочника сотрудников (`employeeService.get(...).orElseThrow()`); нет сотрудника — нет заявки. |
| Дополнительные пассажиры | `joinedPassengerIds` — идентификаторы сотрудников, сервис разрешает их через справочник сотрудников. |
| Копия справочника сотрудников | Сервис заявок получает сотрудников из corporate через Kafka (`EmployeeListenerImpl`, `EmployeeMessage`) и хранит у себя (`database.model.corp.Employee`). |
| Сервис corporate | Сущности: сотрудники, подразделения, должности, организации, цели поездок и др. `Contact` — контакты организации (тип и значение), не физлица. Сущности «клиент-физлицо» нет. |
| Корпоративный кабинет | Справочники: сотрудники, признаки сотрудников, цели поездок, должности, подразделения, контрагенты, филиалы. Справочника клиентов-физлиц нет. Раздел «Клиенты» — корпоративные клиенты (организации, исполнители, договоры, тарифы), это другое. |
| Стенд, 06.11 | В блоке «Кто пассажир?» только «Я» и «Мой коллега»; блока клиентов-физлиц в кабинете нет. |

Поиск по всем репозиториям снимка («Мой клиент», «Мои клиенты», «физлиц», guest, `MY_CLIENT`, `PassengerType`, `nonEmployee` и похожие) ничего относящегося к пассажирам не нашёл.

### 3.2 Проверки, завязанные на пассажира-сотрудника

| Проверка | Как работает сейчас | Что значит для клиента |
|---|---|---|
| Телефон пассажира (`MobilePhoneValidator`) | Все виды. Нет мобильного у пассажира — 400 «Не найден номер мобильного телефона пассажира». | По требованию телефон клиента необязателен — проверку нужно изменить. |
| Отсутствие по ЕАСУП (`checkOnAbsence`) | Такси и трансфер. Запрос в ЕАСУП по табельному номеру пассажира. Заказ себе на время отсутствия — запрет; на коллегу — флаг. | У клиента нет табельного номера — проверка неприменима. |
| Пересечение заявок (`OtherRequestsValidator`) | Такси, личный транспорт, каршеринг (`request.validation.others.enabled-for`). Запрет, если у пассажира есть незавершённая заявка на пересекающееся время (подача … подача + `expected.time`). | Должна считаться по клиенту, иначе нельзя заказать несколько машин на одно время для разных гостей. |
| Лимит многоточечных поездок | Такси и трансфер. Запрет четвёртой за сутки заявки с промежуточными точками у пассажира (request-checks, по `passengerId`). | Решить, считать ли по клиенту. |
| Флаги длительности и пробега | Длительность за сутки (12 ч), пробег за месяц (5 000 км), длительность одной заявки (8 ч, только такси) — по `passengerId` в request-checks, флаг в фрод-мониторинг. | Решить, считать ли по клиенту. |
| Лимиты (бюджет) | Тарифный расчёт проверяет лимит по сотруднику и подразделению (`fillLimitsAvailable`); резервирование в сервисе заявок — для общественного транспорта, личного транспорта, каршеринга. На главной кабинета — виджет «Бюджет»: выделено, использовано, численность. | По требованию клиент не участвует в бюджете: не проверяется по лимитам, ничего не списывает, не входит в использование и численность. |

### 3.3 Что можно сделать без режима

- **Такси на гостя** — только на себя или на коллегу; данные гостя — в комментарии водителю. Водитель звонит сотруднику. Несколько такси на одно время на одного пассажира не создадутся из-за запрета на пересечение заявок.
- **Трансфер** — у заявки есть «Дополнительное контактное лицо» (ФИО и телефон; `GroupTransferRequestInformationDTO.addContactFIO/addContactPhone`). Его видно в «Исполнении заявок» кабинета, и оно передаётся исполнителю. Пассажиром формально остаётся сотрудник. У такси такого поля нет: дополнительная информация сохраняется только для трансфера.
- **Завести гостя сотрудником** технически возможно, но это обход: гости попадут в справочник сотрудников, численность, лимиты, отчёты и проверки.

## 4. Где придётся дорабатывать

| Компонент | Что затрагивается | Комментарий |
|---|---|---|
| Сервис заявок (passenger_request) | Пассажир-клиент в модели заявки, API создания и чтения, событие `service.request`; проверки из 3.2. | Основной объём. |
| Хранение клиентов | Сущность «клиент» в организации. | По описанию заказчика — рядом с сотрудниками, то есть в corporate; либо отдельный сервис. Решает архитектор. |
| Корпоративный кабинет | Справочник «Клиенты физлица» в «Структуре»: список, загрузка, добавление, редактирование. | |
| Клиентская часть WEB (client-passengers) | Режим «Мой клиент» в блоке «Кто пассажир?», выбор и добавление клиента, несколько пассажиров, раздел «заявки для клиента» в «Мои заявки». | |
| Мобильное приложение | То же, что WEB. | Кода МП у проекта нет. |
| Уведомления (notifications, SMS, push) | Уведомления на телефон клиента, если он указан. | Требование «привязать уведомления» не детализировано. |
| Потребители заявки | Согласования, реестры и отчёты, фрод-мониторинг, request-checks и другие подписчики `service.request`. | Проверить, как они читают пассажира. |
| Диспетчерская и приложение водителя | Изменений не требуется (ответ заказчика 09.11). | При условии, что ФИО и телефон клиента приходят в те же поля пассажира, которые диспетчерская читает сейчас. |

**Что не затрагивается:** сервис избранных маршрутов (FavoriteRoute) и его согласованные документы T01.1–T01.4. Экран заказа по избранному маршруту (T02.2) использует штатный блок «Кто пассажир?» и фиксированную цену одинаково во всех режимах; признаки избранного маршрута в заявке от пассажира не зависят.

## 5. Предложения по реализации

Предложения аналитика проекта для обсуждения с командой ДЗО и архитектором.

1. **Пассажир заявки с типом.** Признак типа пассажира (сотрудник / клиент) и идентификатор клиента. Для клиента в заявке сохраняется снимок данных на момент заказа (ФИО, телефон), чтобы последующие правки справочника не меняли историю.
2. **Совместимость полей пассажира.** ФИО и телефон клиента отдаются в те же поля пассажира в API и в событии `service.request`, которые читают диспетчерская, приложение водителя и другие потребители. Тогда диспетчерская работает без изменений, как сказал заказчик.
3. **Несколько пассажиров.** Основной пассажир и дополнительные пассажиры-клиенты; сейчас дополнительные пассажиры (`joinedPassengerIds`) — только сотрудники.
4. **Проверки для клиента:** телефон необязателен; ЕАСУП не применяется; лимиты и бюджет не проверяются и не резервируются; пересечение заявок считается по клиенту. По лимиту многоточечных поездок и флагам длительности и пробега — отдельное решение (по клиенту или не применять).
5. **Справочник клиентов:** организация, фамилия, имя, отчество, телефон (необязателен), признак активности, аудит. Права на ведение — как у справочника сотрудников. Загрузка — по аналогии с загрузкой сотрудников.
6. **Добавление с экрана заказа** сохраняет клиента в справочник организации, чтобы в следующий раз выбрать его из списка.
