# T01.2 — API справочника избранных маршрутов (FavoriteRoute)

**Проект:** Манжерок — фиксированная (прайс-стоимость) поездка по маршруту
**Epic:** TRANSPORT-45584 · **Задача:** TRANSPORT-45586 (T01.2, SP 13, приоритет критичный)
**Редакция:** v1.0, 07.10.2026 · **Статус:** проект спецификации для согласования
**Аналитик:** Нос Яна · **ИТ-лид:** Ярцев Роман

Документ описывает REST API управления записями справочника избранных маршрутов: создание, получение списка, детальное отображение, редактирование и деактивацию. Структура разделов по каждой ручке приведена к формату документации API CRM2.0 (Swagger — Требования — Запрос — Ответ — Описание ошибок).

Пути, DTO, формат страниц и ошибок ниже — **проект для согласования**. Они опираются на соглашения платформы, подтверждённые исходным кодом АС СберТранспорт, но готового API FavoriteRoute в платформе нет, и контракт архитектором не утверждён (Q07). Наличие проектного решения в этом документе не означает, что заказчик или архитектор его согласовал.

## 1 Назначение и границы

### 1.1 Цель

Управлять справочником маршрутов с фиксированной ценой, обеспечить изоляцию организаций, проверку данных и сохранение истории. Справочник переопределяет стандартный расчёт по тарифной сетке (расстоянию) фиксированной стоимостью из записи маршрута.

Управление доступно авторизованным пользователям с доступом к корпоративному кабинету. Отдельная бизнес-роль не выделяется: по протоколу встречи 10.09.2026 (п. 10) «доступ есть у всех, кто авторизован и имеет права», доступ к URL проверяется существующим механизмом платформы `role-check-starter` (связка роль ↔ метод + URL в БД). Формулировка БТ про роль «Управляющий справочниками» (BR-04) этим решением закрыта и в БТ требует правки.

### 1.3 Что входит в объём T01.2

1. Создание записи справочника с выделением человекочитаемого номера.
2. Получение списка записей организации с пагинацией, поиском по номеру и согласованными фильтрами.
3. Детальное отображение записи.
4. Редактирование записи с сохранением истории (разрешено протоколом 10.09.2026, п. 7).
5. Деактивация записи (логическое удаление) с проверкой активных заявок.
6. Серверная валидация бизнес-правил BR-04…BR-08 независимо от ограничений интерфейса.

### 1.6 Решения, подтверждённые заказчиком и не переоткрываемые

1. Первая точка — выезд с базы, последняя — возврат на базу; равенство координат крайних точек не проверяется.
2. Ожидание задаётся у промежуточных точек, хранится внутри элемента точки и фиксируется при создании маршрута (протокол 10.09.2026, п. 3; решение D09). Отдельный массив `wait_times` в целевой модели не нужен.
3. Фиксированная стоимость и расчётная (рекомендуемая) цена — два разных значения, хранятся раздельно (протокол 10.09.2026, п. 5). `fixedCost` задаёт пользователь, значение должно быть больше нуля.
4. Корректировка записи **разрешена** с сохранением в БД автора и времени правки (протокол 10.09.2026, п. 7). Формулировка БТ «корректировка недоступна» закрыта и требует правки в БТ.
5. Для одних и тех же адресов разные вид транспорта, класс услуги или ночной признак — всегда **отдельные записи** с отдельными ID (протокол 10.09.2026, п. 1).
6. «Ночной тариф» и «Период действия маршрута» — два разных поля (протокол 10.09.2026, п. 4).
7. Маршрут не хранит конкретное транспортное средство; выбор автомобиля выполняется при оформлении заявки (протокол 17.09.2026, п. 4).
8. Маршрут не хранит цель поездки: цель — атрибут заявки, её доступность зависит от даты, времени суток и дней недели (протокол 17.09.2026, п. 9; подтверждено кодом `corporate`).
9. Маршрут активен, пока действует связанный тариф; при создании в запись пишется номер тарифа (протокол 17.09.2026, п. 10).
10. Ручное удаление — деактивация с сохранением истории; при активных заявках запрещено, завершённые поездки не препятствуют. Вручную удалённая запись не восстанавливается.
11. Истёкший маршрут не отображается в списке выбора на клиенте; архив истёкших маршрутов не ведётся (протокол 10.09.2026, п. 15).
12. Переименования по протоколу 17.09.2026 (п. 1, 2): `route_number` → `favoriteRoute`, `service_type` → `transportType`.

## 2 API справочника избранных маршрутов

Базовый ресурс — `/api/favorite-routes/{organizationId}/routes`. Версия API и префикс шлюза сверяются с репозиторием (Q07). Для получения, изменения и деактивации используется технический UUID `id`; `favoriteRoute` (человекочитаемый номер) предназначен для отображения и поиска.

| Метод и путь | Назначение | Успех |
|---|---|---|
| `POST /api/favorite-routes/{organizationId}/routes` | Создание записи справочника | 201 |
| `GET /api/favorite-routes/{organizationId}/routes` | Список записей организации | 200 |
| `GET /api/favorite-routes/{organizationId}/routes/{id}` | Детальное отображение записи | 200 |
| `PUT /api/favorite-routes/{organizationId}/routes/{id}` | Редактирование записи | 200 |
| `DELETE /api/favorite-routes/{organizationId}/routes/{id}` | Деактивация записи | 204 |

Общие правила для всех ручек:

1. `organizationId` в path проверяется аспектом `@CheckOrganizationAccess`: организация пользователя из JWT должна совпадать с запрошенной, иначе **403**.
2. Технические поля (`id`, `favoriteRoute`, `createdBy`, `updatedBy`, `createdAt`, `updatedAt`, `isActive`) заполняет сервер. Клиент их не задаёт и не меняет.
3. Расчётные показатели (`totalKm`, `travelTime`, `totalTime`, `recommendedCost`, `freeWaitTime`) сервер получает или проверяет через T01.4, а не принимает как произвольные клиентские числа (Q08).
4. Ошибка не должна оставлять частично сохранённую запись или частично записанную историю.

### 2.1 Создание избранного маршрута — `POST /manager/favorite-routes` → `POST /api/favorite-routes/{organizationId}/routes`

#### 2.1.1 Swagger

Добавить после утверждения контракта (Q07). OpenAPI-описание — условие завершения спецификации (раздел 4).

#### 2.1.2 Требования

1. Пользователь авторизован; доступ к URL разрешён `role-check-starter`; организация из path совпадает с организацией пользователя.
2. Провалидировать наличие и тип всех обязательных полей запроса.
3. Проверить бизнес-правила: число точек от 2 до 10 (BR-06, минимум — риск-реестр БТ п. 13 №2); ожидание обязательно при более чем 2 точках (BR-07); `fixedCost > 0` (риск-реестр БТ п. 13 №1); `serviceClass` допустим для выбранного `transportType`; `validFrom ≤ validTo` при двух заданных границах (BR-08).
4. Применить правило дубля после решения Q01; проверка должна учитывать конкурентное создание.
5. Через T01.4 проверить действующий тариф для территории **первой** точки, вида транспорта, класса и ночного признака. Отсутствие подходящего действующего тарифа запрещает сохранение: в корпоративном кабинете возвращается ошибка «Заведите тариф» (протокол 10.09.2026, п. 11).
6. Получить расчётные показатели: расстояние и время — `POST /api/geo/route`, стоимость и бесплатное ожидание — `POST /api/tariffs/calculate`. Не заменять введённую `fixedCost` расчётной ценой.
7. Вычислить суммарное ожидание по точкам. Не вычитать из суммы бесплатный лимит тарифа.
8. Атомарно выделить номер `FR-XXXX-XXXXXXXX`, где `XXXX` — `digitId` организации автора. Уникальность обеспечивается ограничением `UNIQUE` в БД; генератор платформы от гонки не защищён, механизм блокировки и повтора — Q10.
9. Сохранить запись и начальную запись истории в одной транзакции.
10. Вернуть сохранённую карточку с кодом 201.

### 2.4 Редактирование избранного маршрута — `PUT /api/favorite-routes/{organizationId}/routes/{id}`

#### 2.4.1 Swagger

Добавить после утверждения контракта (Q07).

#### 2.4.2 Требования

1. Пользователь авторизован; организация из path совпадает с организацией пользователя.
2. Проверить наличие записи и допустимость изменения её состояния. Вручную деактивированная запись не восстанавливается через `PUT`. Возможность продлить период и повторно активировать истёкшую запись — **открытое бизнес-решение** (Q04 / D05).
3. Проверить актуальность версии записи. Платформа механизма не предоставляет (`@Version` / `ETag` / `If-Match` не используются, редактирование заявок — «последний выигрывает»), поэтому механизм для FavoriteRoute требуется выбрать (Q11).
4. `PUT` содержит все редактируемые поля; `waypoints` заменяется целиком с сохранением порядка. Семантика пропущенных полей и `null` — Q07.
5. Изменение точек, ожиданий, вида транспорта, класса, ночного признака или параметров тарифа требует актуального расчёта по правилам T01.4. Изменение только названия состав маршрута не меняет и пересчёта не требует.
6. Сохранить `id`, `favoriteRoute` и `createdAt` без изменений; обновить `updatedBy` и `updatedAt`.
7. Сохранить изменения и запись истории атомарно (протокол 10.09.2026, п. 7: в БД фиксируется, кто и когда правил).
8. Изменение записи справочника **не должно задним числом менять данные уже созданных заявок**: для отчётности используется историческая версия или снимок, выбранный в T01.1 (D04 / Q11).
9. Запрет редактирования при активных заявках из подтверждённого запрета удаления **не следует** и автоматически не вводится.

### 2.5 Деактивация избранного маршрута — `DELETE /api/favorite-routes/{organizationId}/routes/{id}`

#### 2.5.1 Swagger

Добавить после утверждения контракта (Q07).

#### 2.5.2 Требования

1. Пользователь авторизован; организация из path совпадает с организацией пользователя.
2. Проверить наличие записи по `id` в таблице `favorite_route` и её принадлежность организации.
3. Проверить наличие активных заявок по маршруту по контракту T04.1. Активными считаются заявки в нетерминальных статусах; по коду платформы это `AWAITING_APPROVAL`, `APPROVED`, `AWAITING_SEARCH`, `DRIVER_SEARCH`, `DRIVER_FOUND`, `DRIVER_ON_THE_WAY`, `DRIVER_ARRIVED`, `TRIP_IN_PROGRESS`, `GENAI_CHECK`, для такси дополнительно `FREE_TIME_EXPIRED` и `WAYPOINT_ARRIVED`; терминальные — `CANCELLED`, `TRIP_FINISHED`. Итоговый состав блокирующих статусов утверждает заказчик (Q12).
4. При наличии активных заявок — отказ **без изменений** в данных.
5. При отсутствии активных заявок — деактивация (`is_active = false`) с записью истории. Данные и история сохраняются, запись не удаляется физически.
6. Проверка и деактивация должны быть согласованы с созданием новой заявки, чтобы исключить гонку. В платформе такого механизма нет — Q12.
7. **Недоступность проверки не означает отсутствие активных заявок**: при сбое зависимости деактивация не выполняется.
8. Повторный `DELETE` для уже деактивированной записи — 204 без дополнительной записи истории (проект).
9. Истёкшая запись не равнозначна вручную деактивированной. Операция восстановления в объём не включена до решения Q04.
10. API поиска заявок по признаку «избранный маршрут» в платформе **нет** (поля нет) — контракт проверки создаётся в T04.1.

### 3.2 Вопросы заказчику

#### Q01 Критерий дубля

**Вопрос.** Какие совпадения делают два маршрута дублями: адреса и порядок точек, ожидания, вид транспорта, класс услуги, ночной признак, период действия, цена? Считать ли записи с разными периодами или разными ценами допустимыми? При совпадении запрещать сохранение или предупреждать?

**Для закрытия.** Отдельные записи для разных вида транспорта, класса услуги и ночного признака уже предусмотрены (протокол 10.09.2026, п. 1). Нужны точный состав сравнения и действие при дубле; от ответа зависят `POST`, `PUT` и защита конкурентной записи, а также состав индекса под проверку дубля.

**Что известно.** Сравнения упорядоченных точек маршрута в платформе нет. Найдены три аналога: при сохранении нового тарифа такси с тем же набором «организация + регион + подразделение + ночь + договор + класс» старый тариф **деактивируется**, а не отклоняется; у трансфера `TRANSFER_CAR_CHOICE` конфликт ищется по пересечению дат (границы включительно), организации, перевозчику, регионам и ТС; у заявок при пересечении интервалов пассажира возвращается `CreateRequestConflictException`. Нормализации адресов для сравнения нет, координаты сравниваются с `EPSILON`.

**Статус.** Ожидает ответа заказчика (состав ключа, запрет или предупреждение) + Ожидает решения архитектора (конкурентная проверка). Техническая часть — закрыт кодом (аналоги).

#### Q02 Период доступности

**Вопрос.** При выборе маршрута проверяем период действия на дату оформления заявки или на плановую дату поездки? В каком часовом поясе трактуем границы периода и ночное окно? Включается ли последний день целиком? Допустим ли маршрут без одной или обеих границ периода?

**Для закрытия.** Нужен единый пример: заявка оформляется до окончания периода, а поездка состоится после. В БД поля `valid_from` / `valid_to` сейчас необязательны; реализация доступности зависит от бизнес-смысла. Правило должно быть одинаковым для списка, карточки и сохранения заявки.

**Что известно.** Тарифы трансфера фильтруются по дате поездки, обе границы включительно (`end >= tripDate AND tripDate >= start`), дата берётся из `tripDate` в UTC после приведения к поясу региона. Договор истекает на следующий день после `endDate` (cron по умолчанию 21:00, пояс JVM не установлен). Ночь — час ∈ [22, 6) в поясе региона первой точки; если ночных тарифов такси нет, берутся дневные. У трансфера ночного признака нет. Календарный период отделён от ночного признака (протокол 10.09.2026, п. 4).

**Статус.** Ожидает ответа заказчика (дата оформления или поездки, часовой пояс, открытые границы) + Ожидает владельца TariffService (пояс JVM шедулера, поведение у полуночи). Техническая часть — закрыт кодом (аналоги).

#### Q03 Список и фильтры

**Вопрос.** Какие фильтры нужны в справочнике? Нужно ли показывать истёкшие маршруты в административном списке и как их отличать? Нужен ли доступ к вручную удалённым записям в интерфейсе?

**Для закрытия.** Макет подтверждает поиск по номеру, пагинацию и наличие кнопки фильтров, но не их состав. История удалённой записи сохраняется независимо от решения о её отображении. Административный список справочника и список маршрутов, доступных для оформления заявки, могут иметь разные правила видимости.

**Что известно.** Пассажирские справочники используют Spring `Pageable`: в тарифах размер по умолчанию 20, сортировка `humanReadableId ASC`, фильтр передаётся телом (`TariffSearchDTO`); поиск заявок — `POST` с DTO фильтра и `Page<>`. В lib `core` есть обёртка `Page{content, pageData, sortData}`. Готовый образец разделения списков — справочник целей поездки в `corporate`: раздельные методы «все активные» (`GET /{organizationId}/purposes`) и «все, включая неактивные» (`/all`), поиск `/search?value=`, пагинации нет. На клиенте отображаются только активные маршруты, истёкший просто не появляется в списке выбора (протокол 10.09.2026, п. 15).

**Статус.** Ожидает ответа заказчика (состав фильтров и видимость) + Ожидает решения архитектора (формат страницы: Spring `Page` или CORE `Page`). Техническая часть — закрыт кодом (соглашения).

#### Q04 Истечение срока действия

**Вопрос.** Можно ли повторно активировать маршрут после окончания срока действия, например изменением периода? Через какую операцию API и с какой повторной проверкой тарифа?

**Для закрытия.** Это то же открытое бизнес-решение, что D05. Вручную удалённые маршруты не восстанавливаются — это закрыто и образцом для истёкших быть не может. Ответ определяет состояния записи и допустимые операции `PUT`.

**Что известно.** Истёкший маршрут недоступен для выбора, его данные сохраняются, архив истёкших не ведётся (протокол 10.09.2026, п. 15). В платформе операции восстановления «удалённого» тарифа нет; договор можно снова сохранить активным методом `save` — на стенде не проверялось.

**Статус.** Ожидает ответа заказчика. Частично закрыт (сценарий ручного удаления закрыт, истечение срока — нет).

#### Q05 Ожидание и число точек

**Вопрос.** Есть ли максимум и шаг задания ожидания? Можно ли оставить его пустым и означает ли это отсутствие ожидания? Допустим ли маршрут только с выездом и возвратом, без промежуточных адресов?

**Для закрытия.** Общие зависимости D02 / D10. Ввод в минутах и хранение внутри точек закрыты. Максимум 10 адресов из БТ сохраняется; новый максимум без основания не запрашиваем. Равенство координат крайних точек не проверяем. API должен проверять согласованные правила независимо от ограничений интерфейса.

**Что известно.** Сервер заявок допускает 2…50 точек, `@Min(0)` стоит на стоимости и расстоянии, проверок `waitTime` нет. В интерфейсе ожидание вводится только в промежуточных точках; при удалении точек до двух ожидание последней обнуляется. У трансфера при `waitTime: null` в любой точке расчёт падает (фильтра `null` нет) — в хранении нужен `0`, а не `null`. Конвертер платформы сериализует `null` как `0`, поэтому различие «пусто» и «ноль» API заявки не сохранит. Заявка с 3 и более точками считается многоточечной, и по умолчанию у пассажира не более 3 таких заявок в сутки. Превышение суммарных 60 минут ожидания запускает асинхронную fraud-проверку (разбирается вручную, создание не блокирует), а не запрет сохранения.

**Статус.** Ожидает ответа заказчика (максимум, шаг, смысл пустого значения, допустимость маршрута «база → база»). Техническая часть — закрыт кодом. Требуется проверка стенда: трансфер с `waitTime: null`.

#### Q06 Тариф перестал действовать

**Вопрос.** Что должен видеть пользователь, если у существующего маршрута больше нет подходящего действующего тарифа: маршрут доступен только для просмотра, скрыт при выборе или помечен недоступным? Кто и когда выявляет истечение тарифа?

**Для закрытия.** Отсутствие тарифа при создании уже блокирует сохранение. Здесь нужен ответ только о существующей записи. Причину недоступности и её отличие от ручного удаления нужно согласовать с T01.4. Фиксированная цена в записи не доказывает, что по ней можно оформить новую заявку при недействительном тарифе.

**Что известно.** Маршрут активен, пока действует тариф (протокол 17.09.2026, п. 10). Сервер заявок берёт тариф из локальной реплики по id: у такси — без проверки признака активности, у трансфера — проверяется только `minCreateTime`. Удалённый тариф такси удаляется из реплики (сообщение `deleted`) → при оформлении 404; трансфер при удалении шлёт обычное сообщение, запись в реплике остаётся. Истечение договора события не порождает. Предварительный расчёт `/tariffs/calculate` исключает тарифы с неактивным договором.

**Для закрытия.** Нужны метод, единицы, округление и защита диапазонов, преобразование результата в поля API, серверная проверка актуальности расчёта. Момент пересчёта формы уточнить с T01.3. Предположение «пересчёт после нажатия Сохранить» подтверждённым контрактом не является.

#### Q10 Номер и повтор создания

**Адресат.** Разработчик API и архитектор.

**Вопрос.** Как генерируется `FR-XXXX-XXXXXXXX` без коллизий, как обрабатываются `digitId` и предел счётчика? Какой механизм повторного `POST` после потери ответа принят в платформе?

**Для закрытия.** Атомарная нумерация, идемпотентность и конкурентная проверка дубля после Q01.

**Что известно.** Формат совпадает с платформенным (`OT-0001-00000001`, `TF-…`). Библиотека `human-readable-generator`: `getNextId(prefix, orgDigitId)` → `PP-DDDD-NNNNNNNN`, счётчик в `company_sq` на каждый сервис, уникальность `(prefix, orgDigitId)` и `(prefix, orgDigitId, sq)`, `digitId` 1…9999, префикс ровно 2 символа. `digitId` берётся из организации **автора** (сотрудник → подразделение → организация) и клиентом не принимается; организация с `digitId > 9999` номер получить не сможет. **Исправление вывода:** механизм установлен и защиты от гонки не имеет — счётчик читается и пишется вне транзакции вызывающего (`@Transactional(NOT_SUPPORTED)`), последовательностью «найти → увеличить → сохранить» без блокировки строки; `@Version` нет; объявленный метод `…ForWrite` без `@Lock`/`FOR UPDATE` генератором не используется; конкурентных тестов нет. Два одновременных вызова для одной организации могут получить одинаковый номер — защитой остаётся уникальный индекс номера в целевой таблице (в T01.1 он есть), второй запрос упадёт на ограничении и потребует повтора. При счётчике > 99 999 999 формат не обрезается и шаблон `FR-XXXX-XXXXXXXX` нарушится (`varchar(20)` это вмещает). Альтернативная реализация в `corporate` использует `synchronized` (в пределах одного экземпляра JVM) и проверку занятых номеров; как образец не годится — в ней есть обновление `company_sq` без условия `WHERE`.

**Статус.** Ожидает решения архитектора (блокировка `SELECT … FOR UPDATE` / advisory-lock / последовательность БД, повтор при конфликте, поведение после 99 999 999). Техническая часть — закрыт кодом.
