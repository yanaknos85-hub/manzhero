# Результаты проверок на стенде 18.11.2026

Проверки по списку от 18.11 (15 вопросов). Смотрели обычную форму заказа WEB (такси, трансфер, «Поездка в личных целях»), список поездок сотрудника, отмену трансфера и корпоративный кабинет «Исполнение заявок» (такси и трансфер). Ответы API снимались во вкладке Network.

Не проверялись: справочник избранных маршрутов, мобильное приложение, кабинет диспетчера. Персональные данные из ответов (ФИО, телефоны, табельные номера) в файл не переносились.

## 1. Главное

| № | Что увидели | Насколько важно | Что делать |
|---|---|---|---|
| 1 | **Точка без здания.** В обычной форме при выборе точки на карте часть запросов `GET /api/geo/address?latitude=…&longitude=…` завершилась ошибкой: в Network они выделены красным, статус на скриншоте не виден. По коду geo, если 2ГИС не нашёл здание, сервис отвечает 417, а не `200 []`. Если на стенде это действительно 417, то для первой точки без здания (например, село из подсказок) FavoriteRoute по T01.2 вернёт 502 «технический сбой», а не 400 «Не удалось подтвердить здание по выбранному адресу». Подсказка «Выберите другой адрес из подсказок» тогда не появится, а повтор не поможет. С этим согласуется прежняя проверка с первой точкой «Простоквашино»: она закончилась ошибкой зависимости. | **Возможно, критично.** Нужно подтвердить статус. | 1) Открыть красный запрос `address?latitude=…`, посмотреть Status Code на вкладке Headers и тело на вкладке Response. 2) В справочнике выбрать первой точкой село и посмотреть ответ FavoriteRoute: 400 или 502. Если подтвердится 417 — решать с архитектором до приёмки T01.2. Правку T01.2 вносить только по этому решению. |
| 2 | **Формат `creationTime` в Kafka, косвенно.** Реестр «Исполнение заявок» строится из копии событий `service.request`. У всех 10 заявок в реестре доля секунды либо 0, либо ровно 0,000001 с. Так получается, если источник пишет долю в миллисекундах, а потребитель читает её как наносекунды: 500–999 мс превращаются в 500–999 нс и округляются до 1 мкс. Значит, на стенде `creationTime` в Kafka — массив, доля в миллисекундах. Действующий потребитель реестров при этом теряет миллисекунды. **Подтверждено 19.11 сверкой двух заявок:** OT-0013-00000848 — в REST 12:46:09.974Z, в реестре 12:46:09.000001Z; OT-0013-00000845 — в REST 12:59:26.628Z, в реестре 12:59:26.000001Z. | Для FavoriteRoute не критично: доли секунды не влияют на окна N и M. Критично было бы, если бы поле приходило строкой вместо массива, но косвенные данные говорят за массив. | В потребителе FavoriteRoute явно читать долю секунды как миллисекунды. Подтвердить реальным сообщением: вопрос Сберу о реальных событиях остаётся. |
| 3 | **Незавершённые заявки трансфера не закрываются.** Трансферы с датами 30.09, 06.11 и 12.11 на 18.11 всё ещё в статусе «Ожидайте назначения водителя» (`GROUP_TRANSFER_AWAITING_SEARCH`): на стенде их никто не исполняет. По T01.2 незавершённая связанная заявка блокирует деактивацию маршрута. | Не дефект, но мешает приёмке | На приёмке отменять тестовые заявки. Отмена работает, см. вопрос 4. |

## 2. Ответы по вопросам

| № | Вопрос | Результат | Статус |
|---|---|---|---|
| 1 | В каком виде сервис заявок отдаёт даты | `GET` заявки отдаёт `creationTime` и `desiredDate` числом: epoch в миллисекундах по UTC. Например, заявка, созданная в 15:46 МСК, имеет `creationTime` = 12:46:09.974Z. Этот формат задан конвертером в DTO REST, поэтому формат Kafka по REST не определить: предпосылка проверки была неверной. Косвенный признак формата Kafka — раздел 1, п. 2. | Получено, для Kafka не показательно |
| 2 | Как отдаются длительности | `expected.time` и `segments[].time` — числа в миллисекундах (693000, 8000), `waitTime` — число. Это тоже конвертеры DTO, для Kafka не показательно. | Получено, не показательно |
| 3 | Пустые поля: пропуск или null | В ответе сервиса заявок ключей со значением null нет, пустые поля опускаются. В реестре кабинета, это другой сервис, null передаются явно. Для сервиса заявок это согласуется с настройкой «пустые поля не выводить». Скорее всего, сброс ссылки на маршрут в Kafka будет выглядеть как отсутствие ключей. Подтвердить реальным сообщением. | Косвенно |
| 4 | Имена статусов, терминальные статусы | Подтверждены имена `GROUP_TRANSFER_AWAITING_SEARCH`, `TAXI_TRIP_FINISHED`, `TAXI_CANCELLED`. 19.11 в реестре, который строится из `service.request`, подтверждены также `GROUP_TRANSFER_CANCELLED` (OT-0013-00000845) и `GROUP_TRANSFER_APPROVED` (OT-0013-00000850). В кабинете они отображаются как «Согласована», «Ожидайте назначения водителя», «Отменено», «Поездка завершена». Отмена трансфера — `PUT /api/requests/cancel/{id}` с телом `{reason, code}`, ответ 200 без тела. Отменённая заявка уходит из списка активных (`non_terminal`), то есть отмена терминальна. Имя `GROUP_TRANSFER_CANCELLED` в JSON не снималось. | Подтверждено частично |
| 5 | Видит ли пользователь заявку другого автора | Не проверялось. Реестр кабинета показывает заявки других сотрудников, но это другой API. | Открыто |
| 6 | Сохраняется ли `information` у такси | Снят только трансфер, такси не проверялось. У трансфера `information` сохраняется, `addContactFIO` и `addContactPhone` заполнены. | Открыто для такси |
| 7 | Нет лимита или лимит исчерпан | Не проверялось | Открыто |
| 8 | Нет мобильного телефона в профиле | Не проверялось | Открыто |
| 9 | Пересечение заявок такси | Не проверялось | Открыто |
| 10 | Режим по умолчанию | В обычной форме WEB при открытии выбрано «Как можно скорее». В блоке «Кто пассажир?» только «Я» и «Мой коллега», режима «Мой клиент» нет. Переключатель «Поездка в личных целях» есть. МП не проверялось. | Подтверждено для WEB |
| 11 | Подписи точек в МП | Не проверялось | Открыто |
| 12 | Контакт гостя у диспетчера | Не проверялось: в тестовом трансфере контакт совпадает с пассажиром, кабинет диспетчера не открывался. В трансфере обычной формы обязательны: количество пассажиров, контакт — ФИО (или фраза «Нет пассажира») и телефон, количество багажа. | Открыто |

По строке «ленина 5» при работе из Москвы пришли Красногорск и Липецк: без населённого пункта в строке подсказки к региону не привязаны. ## 3. Наблюдения вне списка

- **Трансфер обычной формы.** `outcomeTariffId` равен `tariffId` — подтверждает проверку 06.11. Расходная стоимость меняется: 06.11 ответ на создание заявки OT-0013-00000845 содержал `expected.outcomeCost` = 400 ₽ (равна `cost`), а 18.11 `GET` той же заявки после согласования показывает 0. Кто и когда обнуляет расходную стоимость штатной заявки, неизвестно. Для T04.2 это важно: расходную стоимость заявок по ИМ проставляет бэкенд.
- **Проверка отсутствия сотрудника.** Запрос `check-absence` по-прежнему завершается ошибкой без ответа. 06.11 из-за этого кнопка заказа блокировалась, 18.11 заказ трансфера прошёл. Поведение самой проверки на стенде проверить нельзя.
- **Часовой пояс.** Пояс в заявке передаётся строкой `GMT+03:00`.
