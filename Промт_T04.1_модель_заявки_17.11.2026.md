# Промпт: T04.1 «Расширение модели заявки для избранных маршрутов»

Ты системный аналитик проекта «Избранные маршруты» АС «СберТранспорт», Манжерок. Подготовь спецификацию T04.1: какие изменения нужны в сервисе заявок — модели заявки (order), её API и событии, — чтобы заявка, созданная по избранному маршруту (ИМ), хранила связь с маршрутом и обрабатывалась по особым правилам. Документ описывает только изменения сервиса заявок. Задачи других участников (T01.2, T02.3, T04.2, T05.1) не описывай — только укажи зависимости. По спецификации проект пишет код и передаёт его заказчику: код изменений контракта должен быть у заказчика 18.11.2026, крайний срок по контрактам — 19.11.2026. Поэтому сначала зафиксируй контракт (поля, DTO, событие), затем остальное.

## Требования из согласованных документов

1. Ссылка на маршрут. Заявка хранит пару favoriteRouteId (UUID) и favoriteRouteVersion (целое ≥ 0, int64; версия 0 допустима). Пара заполняется целиком или отсутствует целиком. Заявка без ИМ — обе пустые; существующие заявки не меняются. (T01.1, T01.2 §6, T02.2)
2. Чтение и событие. Пара возвращается в ответе чтения заявки по id и передаётся в каждом событии service.request вместе с полным состоянием заявки. FavoriteRoute использует из события поля id, organizationId, favoriteRouteId, favoriteRouteVersion, status и creationTime (момент создания в UTC). Имена и формат этих полей должны совпадать с T01.2. (T01.2 §6)
3. Сброс ссылки. Если у созданной заявки по ИМ меняются точки, заявка переходит на динамический расчёт, а ссылка сбрасывается — в событии её нет. Условие сброса и пересчёт стоимости определяет T04.2; T04.1 задаёт состояние полей после сброса (оба пустые) и то, что сброс отражается в событии и при чтении. Клиент при изменении заявки пару не задаёт и не меняет. (T01.1, T01.2 §6, T02.2)
4. Исключения проверок. Для заявок по ИМ не выполняются: проверка ожидания такси, лимит многоточечных поездок, запрет на пересечение заявок одного пассажира; лимиты сотрудника не проверяются. Обязательные поля, права пользователя и организация проверяются. Признак заявки по ИМ — заполненная пара из п. 1. Найди в коде, где выполняются эти проверки, и опиши точку изменения. (T02.2, решения 11.11 п. 12)
5. Путь маршрута. Для заявок по ИМ expected.segments обязательны — правило валидации при создании. (T02.2)
6. Данные гостя TAXI. Сервис заявок сохраняет блок information для TAXI, включая переданные данные контактного лица (information.addContactFIO, information.addContactPhone). Сейчас блок information есть в запросе создания (NewRequestDTO), но хранится только у заявки на трансфер (RequestForGroupTransfer); у такси он не сохраняется — опиши изменение. Поле passengerCount уже есть в запросе, ответе и модели такси — его не добавляй. (T02.2)
7. Поля БТ вне T04.1. original_fixed_cost и cost_variance_flag относятся к T04.2 (стоимость, план/факт), признак is_favorite_trip для фильтра реестра — к T05.1. В T04.1 их не описывай, только перечисли в зависимостях. Учти для зависимостей: если признак реестра вычислять по паре id/version, после сброса ссылки он пропадёт — это решается в T04.2 или T05.1.
8. Прочие реквизиты ИМ (номер маршрута, tariffId, isNightTariff) в T04.1 не добавляются: заявка хранит только пару id/version, остальное читается из версии маршрута (T01.2). T02.2 передаёт их, «если их предусмотрит T04.1», — укажи, что не предусмотрены.

## Вопросы, которые нужно закрыть в спецификации

1. Проверка ожидания такси. В сервисе заявок она не найдена; формулировка «флаг ожидания такси» тоже требует подтверждения. Найди, где она выполняется (request-checks, другой сервис или фронт формы заказа), и опиши, как она отключается для заявок по ИМ. Если не найдёшь — вынеси в открытые вопросы с перечнем мест, где искал.
2. Что входит в «лимиты сотрудника», которые по T02.2 для заявок по ИМ не проверяются. Предложение: лимит длительности поездок (`checkDurationLimit`) и лимит суммарного километража (`checkOverrunLimit`) для заявок по ИМ не вызываются. Порог длительности одной поездки (`checkSingleTripDuration`) — это защита от мошенничества, а не лимит сотрудника; маршрут с длительными ожиданиями (например, экскурсия) будет получать fraud-запись при каждом заказе. Применять ли его к заявкам по ИМ — вынеси как «предложение на согласование» с обоими вариантами.
