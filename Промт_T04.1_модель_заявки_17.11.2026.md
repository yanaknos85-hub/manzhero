# Промпт: T04.1 «Расширение модели заявки для избранных маршрутов» (TRANSPORT-45593)

Ты системный аналитик проекта «Избранные маршруты» АС «СберТранспорт», Манжерок. Подготовь спецификацию T04.1: какие изменения нужны в сервисе заявок — модели заявки, её API и событии, — чтобы заявка, созданная по избранному маршруту (ИМ), хранила связь с маршрутом и обрабатывалась по особым правилам. Документ описывает только изменения сервиса заявок. Работы других задач (T01.2, T02.3, T04.2, T05.1) не описывай — только укажи зависимости.

По спецификации проект пишет код и передаёт его заказчику: код изменений контракта должен быть у заказчика 18.11.2026, крайний срок по контрактам — 19.11.2026. Поэтому сначала зафиксируй контракт (поля, DTO, событие), затем остальное.

## Временное решение для гостя

До реализации режима «Мой клиент» действует согласованный минимальный вариант:
- пассажиром заявки остаётся сотрудник, оформляющий заказ;
- ФИО и телефон гостя вносятся отдельными полями заявки — как «Дополнительное контактное лицо» у трансфера (блок information);
- для заявок по ИМ снимается запрет на несколько заявок одного пассажира на одно время;
- ограничения: нет сохранённого списка клиентов, уведомления на телефон гостя не приходят, в отчётах пассажиром будет сотрудник; бюджет считается по сотруднику.

В п. 1.1 спецификации прямо укажи, что решение временное и будет заменено режимом «Мой клиент».

## Требования

1. Ссылка на маршрут. Заявка хранит пару favoriteRouteId (UUID) и favoriteRouteVersion (целое ≥ 0, int64; версия 0 допустима). Пара заполняется целиком или отсутствует целиком. Заявка без ИМ — обе пустые; существующие заявки не меняются. Версии в БТ нет, но её требуют T01.1 и T01.2. (T01.1, T01.2 §6, T02.2)
2. Чтение и событие. Пара возвращается в ответе чтения заявки по id и передаётся в каждом событии service.request вместе с полным состоянием заявки. FavoriteRoute использует из события поля id, organizationId, favoriteRouteId, favoriteRouteVersion, status и creationTime (момент создания в UTC). Имена и формат этих полей должны совпадать с T01.2. (T01.2 §6)
3. Поля из декомпозиции. Поля сущности Order из TRANSPORT-45593 входят в T04.1 как поля модели: favorite_route_id — это п. 1; is_favorite_trip, original_fixed_cost, cost_variance_flag — добавить. Заполнение original_fixed_cost и cost_variance_flag (правила BR-09–BR-11) и значение is_favorite_trip после сброса привязки определяет T04.2. Предложение на согласование: is_favorite_trip = true при создании, если передана пара id/version. Перечень декомпозиции — минимальный: модель расширяется и другими полями (п. 1, 6).
4. Две таблицы. Заявки на такси и трансфер — разные сущности в разных таблицах: базовый класс Request использует наследование TABLE_PER_CLASS, такси — request.request_for_taxi, трансфер — request.request_for_group_transfer. Новые поля нужны в обеих таблицах. Реши и обоснуй, где их объявить: в базовом классе (столбцы появятся во всех таблицах заявок, в том числе где ИМ не бывает) или в двух конкретных сущностях. Проверь, нужны ли поля в таблицах истории заявок такси и трансфера.
5. Сброс ссылки. Если у созданной заявки по ИМ меняются точки, заявка переходит на динамический расчёт, а ссылка сбрасывается. Условие сброса определяет T04.2; T04.1 задаёт состояние полей после сброса (оба пустые) и то, что сброс отражается в событии и при чтении. Клиент при изменении заявки пару не задаёт и не меняет.
6. Данные гостя TAXI. Блок information (addContactFIO, addContactPhone) сохраняется для TAXI так же, как у трансфера: новый столбец в таблице такси. Блок отдаётся при чтении заявки и передаётся в событии service.request, чтобы диспетчерская и приложение водителя при необходимости могли показать контакт гостя (сам показ — вне T04.1). Поле passengerCount уже есть — не добавляй.
7. Путь маршрута. Для заявок по ИМ expected.segments обязательны — правило валидации при создании. (T02.2)
8. Проверки при создании заявки по ИМ. Принцип: снимаются ограничения маршрута, времени и количества поездок — маршрут и цена согласованы в справочнике. Сохраняются проверки, без которых поездку нельзя выполнить, и правила компании. Признак заявки по ИМ — заполненная пара из п. 1. Опиши для каждой проверки точку изменения в коде.

   | Проверка | Где в коде | Такси / трансфер | Сейчас | Для заявок по ИМ |
   |---|---|---|---|---|
   | Пересечение заявок пассажира по времени | `OtherRequestsValidator`, включается настройкой `request.validation.others.enabled-for` (TAXI, PERSONAL, CARSHARING) | да / нет | Отказ 409 | Снимается (решение 11.11) |
   | Лимит многоточечных поездок | `AbstractTransportTypeService.checkMultipointLimit` → request-checks | да / да | Отказ на четвёртую за сутки | Снимается |
   | Флаг ожидания такси | `RequestForTaxiServiceImpl.checkTotalWaitTime`, асинхронно | да / нет | Fraud `TAXI_WAITING_TIME` | Снимается |
   | Лимит длительности поездок | `checkDurationLimit` → request-checks | да / да | Fraud `DURATION` | Снимается |
   | Лимит суммарного километража | `checkOverrunLimit` → request-checks | да / да | Fraud с километражем | Снимается |

9. Прочие реквизиты ИМ (номер маршрута, tariffId, isNightTariff) не добавляются: остальное читается из версии маршрута по паре id/version (T01.2). T02.2 передаёт их, «если их предусмотрит T04.1», — укажи, что не предусмотрены.

## Правила

- T01.1, T01.2, T02.2/T03.2 не меняй. Если для T04.1 чего-то не хватает в них, вынеси в открытые вопросы.
- Устаревшие формулировки БТ не переноси: внешнего ключа на FavoriteRoute нет — это отдельный сервис, ссылка логическая (T01.1); тип стоимости бери по тому, как сервис заявок хранит стоимость сейчас, а не «decimal» из БТ.
- Изменения существующих сервисов — минимальные и обратно совместимые; новые поля необязательные.
- Требований сверх перечисленного не добавляй. Пометь «предложение на согласование»: заполнение isFavoriteTrip при создании (п. 3), отключение проверки отсутствия сотрудника (п. 8), выбор места объявления полей (п. 4).
- В примерах не используй персональные данные, токены и адреса стендов.
- Ссылайся только на проектные документы и код; обсуждения и стенд не упоминай.
