# API справочника избранных маршрутов

T01.2 • Проект спецификации v0.7 от 8 октября 2026 года • TRANSPORT-45586 • Эпик TRANSPORT-45584

Документ описывает REST API управления записями справочника избранных маршрутов: создание, получение списка, детальное отображение, редактирование и деактивацию.

Пути, DTO, формат страниц и ошибок ниже — проект для согласования. Они опираются на соглашения платформы, подтверждённые исходным кодом АС СберТранспорт, на решениях архитектора от 08.10.2026 и на обследовании кода, но готового API FavoriteRoute в платформе нет. Наличие проектного решения в этом документе не означает, что заказчик или архитектор его согласовал. Каждое неподтверждённое место помечено ссылкой на номер вопроса — «вопрос архитектору N» или «вопрос заказчику N» по сквозной нумерации редакции 8 списка вопросов архитектору и сводного списка вопросов заказчику.

## 1 Назначение и границы

### 1.1 Цель

Управлять справочником маршрутов с фиксированной ценой, обеспечить изоляцию организаций, проверку данных и сохранение истории. Справочник переопределяет стандартный расчёт по тарифной сетке (расстоянию) фиксированной стоимостью из записи маршрута.

Управление доступно авторизованным пользователям с доступом к корпоративному кабинету. Отдельная бизнес-роль не выделяется: по протоколу встречи 10.09.2026 (п. 10) доступ есть у всех, кто авторизован и имеет права; доступ к URL проверяется существующим механизмом платформы `role_check_starter` (связка роль ↔ метод + URL в БД). Формулировка БТ про роль «Управляющий справочниками» (BR-04) этим решением закрыта и требует правки в БТ; роль с таким названием в коде платформы не найдена, поэтому какая именно роль даёт право — вопрос архитектору 14.

### 1.3 Что входит в объём T01.2

1. Создание записи справочника с выделением человекочитаемого номера.
2. Получение списка записей организации с пагинацией, поиском по номеру и согласованными фильтрами.
3. Детальное отображение записи.
4. Редактирование записи с сохранением истории (разрешено протоколом 10.09.2026, п. 7).
5. Деактивация записи (логическое удаление) с проверкой активных заявок.
6. Предварительный расчёт без сохранения — для кнопок формы (вопрос архитектору 18).
7. Серверная валидация бизнес-правил независимо от ограничений интерфейса.

### 1.6 Решения, подтверждённые и не переоткрываемые

1. Точек в маршруте от 2 до 26, включая базу. Первая точка — место базирования (гараж, отель), последняя — конечная; для маршрутов с возвратом совпадает с базой (встреча 05.10, 10:24–12:04). Равенство координат крайних точек не проверяется.
2. Ожидание задаётся у промежуточных точек, хранится внутри элемента точки и фиксируется при создании маршрута (протокол 10.09.2026, п. 3). На первой и последней точках ожидания нет (встреча 05.10). Отдельный массив `wait_times` в целевой модели не нужен.
3. Фиксированная стоимость по прайсу и расчётная (рекомендуемая) цена — два разных значения, хранятся раздельно (протокол 10.09.2026, п. 5). Прайс вводится вручную, должен быть больше нуля и может быть изменён после расчёта (BR-05).
4. Рекомендуемая стоимость — ориентир по тарифу; цену поездки задаёт прайс. В справочнике она обязательна (встреча 05.10, 09:13–09:25), пользователю при оформлении не показывается (на подтверждении — вопрос заказчику 2).
5. Без расчёта маршрут не сохраняется; значения расчёта от клиента не принимаются (T01.1, D12).
6. Корректировка записи разрешена, в БД сохраняется, кто и когда правил (протокол 10.09.2026, п. 7). Для отчётности используются данные маршрута на дату создания заявки (п. 9).
7. Для одних и тех же адресов разные вид транспорта, класс услуги или ночной признак — всегда отдельные записи с отдельными ID (протокол 10.09.2026, п. 1).
8. «Ночной тариф» и «Период действия маршрута» — два разных поля (протокол 10.09.2026, п. 4). Период можно не задавать: круглогодичные маршруты допускаются (встреча 05.10, 12:07–12:17).
9. Истечение срока определяется по `valid_to` при чтении; `is_active` не меняется, фоновый перевод не выполняется (T01.1, D14).
10. Удалённая и истёкшая записи доступны только для чтения. Вручную удалённая запись не восстанавливается.
11. Истёкший маршрут не отображается в списке выбора на клиенте; архив истёкших не ведётся (протокол 10.09.2026, п. 15).
12. Маршрут не хранит конкретное транспортное средство; выбор автомобиля выполняется при оформлении заявки (протокол 17.09.2026, п. 4).
13. Маршрут не хранит цель поездки: цель — атрибут заявки, её доступность зависит от подразделения, даты, времени суток и дней недели (протокол 17.09.2026, п. 9).
14. Маршрут активен, пока действует связанный тариф; в записи хранится клиентский тариф «на входе», тариф перевозчика в маршрут не попадает (протокол 17.09.2026, п. 10; встреча 05.10, около 01:24).
15. Название точки `name` — необязательное поле; хранится в справочнике и виджете, в заявку и перевозчику не передаётся (встреча 05.10, 09:40–10:11; вопрос архитектору 8).
16. Адрес точки хранится по значению, без id адреса (T01.1, D01).
17. Вид транспорта: поле `service_type` переименовано в `transportType` (протокол 17.09.2026, п. 2 — зафиксировано дословно).
18. Номер маршрута: протокол 17.09.2026 (п. 1) фиксирует само переименование `route_number`, но **точного имени поля не называет**. Имя подтверждённым решением не является ни в одну сторону — T01.1, колонка favorite_route_number. В таблицах ниже используется рабочее `favoriteRouteNumber`, как в колонке `favorite_route_number` актуальной редакции T01.1.

## 2 API справочника избранных маршрутов

Внешний базовый ресурс — `/api/favorite-routes`. Организация определяется по токену и в пути не передаётся. Для получения, изменения и деактивации используется технический UUID `id`; человекочитаемый номер предназначен для отображения и поиска.

| Метод и путь | Назначение | Успех | Основание |
|---|---|---|---|
| `POST /api/favorite-routes` | Создание записи справочника | 201 | Карточка TRANSPORT-45586 |
| `GET /api/favorite-routes` | Список записей организации | 200 | Карточка TRANSPORT-45586 |
| `GET /api/favorite-routes/{id}` | Детальное отображение записи | 200 | Карточка TRANSPORT-45586 |
| `PUT /api/favorite-routes/{id}` | Редактирование записи | 200 | В карточке метода нет; изменение разрешено протоколом 10.09.2026, п. 7. Карточку дополнить (вопрос архитектору 15) |
| `DELETE /api/favorite-routes/{id}?version=n` | Деактивация записи | 204 | Карточка TRANSPORT-45586; способ передачи версии — вопрос архитектору 15 |
| `POST /api/favorite-routes/calculate` | Предварительный расчёт без сохранения | 200 | В карточке метода нет (вопрос архитектору 18) |

Общие правила для всех ручек.

1. Пользователь определяется по токену; организация — по цепочке «учётная запись → сотрудник → подразделение → организация» в локальных таблицах сервиса (в токене организации нет — вопрос архитектору 24). Запись другой организации недоступна: ответ **404**, запись не раскрывается (вопрос архитектору 14). `organizationId`, присланный в теле и не совпадающий с организацией пользователя, — 403 (вопрос архитектору 16).
2. Доступ к паре «метод + URL» проверяет `role_check_starter`. Регистрация новых пар в сервисе ролей — отдельный пункт поставки.
3. Технические поля (`id`, номер, `version`, `createdBy`, `updatedBy`, `createdAt`, `updatedAt`, `isActive`) заполняет сервер. Клиент их не задаёт и не меняет; присланные игнорируются (вопрос архитектору 16).
4. Расчётные показатели (`totalKm`, `travelTime`, `totalTime`, `recommendedCost`) сервер вычисляет сам при каждом сохранении; значения клиента не принимаются (T01.1, D12; вопрос архитектору 7).
5. Ошибка не должна оставлять частично сохранённую запись или частично записанную историю. Транзакция не начинается до получения результата расчёта.

### 2.1 Создание избранного маршрута — `POST /api/favorite-routes`

#### 2.1.1 Swagger

Добавить после утверждения контракта (вопрос архитектору 13).

#### 2.1.2 Требования

1. Пользователь авторизован; доступ к URL разрешён `role_check_starter`; организация пользователя определена по локальной цепочке (вопрос архитектору 24).
2. Провалидировать наличие и тип всех обязательных полей запроса.
3. Проверить бизнес-правила: число точек от 2 до 26; ожидание допустимо только на промежуточных точках; `fixedCost > 0`; `serviceClass` допустим для выбранного `transportType`; `validFrom ≤ validTo` при двух заданных границах; период может быть не задан.
4. Проверить дубль: активная запись организации с тем же набором точек по порядку (по координатам), тем же видом транспорта, классом услуги и ночным признаком и пересекающимся периодом действия. Истёкшие и вручную удалённые записи при сравнении не учитываются. Критерий — вопрос заказчику 4, действие при дубле — вопрос заказчику 7, защита от конкурентного дубля — вопрос архитектору 19.
5. Найти действующий тариф по организации, региону первой точки, классу и ночному признаку через `POST search`. Отсутствие подходящего действующего тарифа запрещает сохранение: возвращается ошибка «Заведите тариф» (протокол 10.09.2026, п. 11). Правило выбора при нескольких найденных тарифах — вопрос архитектору 1; расхождение `search` со штатным подбором — вопрос архитектору 26.
6. Получить расчётные показатели: расстояние и время — `POST /api/geo/route`; стоимость — `POST /api/tariffs/calculate/{transportTypeUUID}/{tariffId}`. Условная дата расчёта — вопрос заказчику 16 и T01.4. Не заменять введённую `fixedCost` расчётной ценой.
7. Вычислить суммарное ожидание по точкам; сложить его со временем в пути, округление half-up один раз после суммирования. Бесплатный лимит тарифа из суммы не вычитать.
8. Атомарно выделить номер `FR-XXXX-XXXXXXXX`, где `XXXX` — `digitId` организации автора. Уникальность обеспечивается ограничением `UNIQUE` в БД; генератор платформы от гонки не защищён, механизм блокировки и повтора — T01.1, D13.
9. Сохранить запись и начальную запись истории в одной транзакции; `version` при создании — 0.
10. Вернуть сохранённую карточку с кодом 201.

#### 2.2.1 Swagger

### 2.5 Деактивация избранного маршрута — `DELETE /api/favorite-routes/{id}?version=n`

#### 2.5.1 Swagger

Добавить после утверждения контракта (вопросы архитектору 13 и 15).

#### 2.5.2 Требования

Порядок проверок задан и важен (вопрос архитектору 17):

1. Пользователь авторизован; организация пользователя определена по локальной цепочке. Запись не найдена или принадлежит другой организации — **404**.
2. Запись уже деактивирована — **204** без проверки версии и без новой записи истории. Повтор безопасен.
3. `version` не совпадает с версией в БД — **409**.
4. По маршруту есть активные заявки — **409**, без изменений в данных. **Активной считается заявка в нетерминальном статусе.** У статуса есть признак `terminal`; для такси и группового трансфера терминальны только «отменена» (`CANCELLED`) и «завершена» (`TRIP_FINISHED`), всё остальное — активная заявка. Перечислять статусы в контракте не нужно: правило опирается на признак. Контракт проверки и защита от гонки — вопрос архитектору 20. Заявка, зависшая на согласовании, по этому правилу блокирует деактивацию — подтверждение у заказчика, вопрос заказчику 17.
5. Иначе — деактивация (`is_active = false`) с записью истории в одной транзакции. Данные и история сохраняются, запись не удаляется физически; `version` увеличивается.
6. Проверка и деактивация должны быть согласованы с созданием новой заявки, чтобы исключить гонку: заявка хранит `favorite_route_version`, деактивация меняет версию (вопрос архитектору 20).
7. **Недоступность проверки не означает отсутствие активных заявок**: при сбое зависимости деактивация отклоняется, а не выполняется.
8. Истёкшая запись не равнозначна вручную деактивированной. Операция восстановления в объём не включена.
9. API поиска заявок по признаку избранного маршрута в платформе нет — поля в заявке ещё нет; контракт создаётся в T04.1.

5. Значения носят справочный характер: при сохранении сервер считает заново и возвращает сохранённые. Если они отличаются от показанных, форма показывает именно сохранённые (вопрос архитектору 18).

### 2.7 Массовый импорт из Excel — `POST /api/favorite-routes/import`

**Проект, не подтверждён.** Требование есть, задачи в декомпозиции нет, реализация у разработчика есть. Описано, чтобы реализованное поведение было зафиксировано письменно и сверено с ответами. Объём и правила — **вопрос заказчику 11**, контракт — **вопрос архитектору 22**.

#### 2.7.1 Требования (проект, по отчёту разработчика от 05.10)

1. Пользователь авторизован; право на загрузку — то же, что на управление справочником (вопрос заказчику 11, п. 4).
2. Формат — Excel; шаблон содержит те же поля, что заведены в справочнике; все участвующие поля должны быть заполнены (протокол 17.09.2026, п. 11).
3. Каждая строка проходит те же проверки и тот же расчёт, что при создании через `POST`.
4. Частичной загрузки нет: любая ошибка отклоняет весь файл, в ответе — перечень ошибок по строкам (вопрос заказчику 11, п. 2).
5. Предел 80 маршрутов: 81-й отклоняется. Является ли 80 жёстким пределом или стартовым объёмом — вопрос заказчику 11, п. 1.
6. Номера выделяются тем же счётчиком, что при создании. При последовательной обработке достаточно штатного генератора; при параллельной требуется атомарный счётчик (T01.1 D13 и вопрос архитектору 19).
7. Обработка синхронная; при 26 точках в строке время расчёта может быть значительным (вопрос архитектору 22 и замер времени расчёта (T01.4)).

#### 2.7.2 Запрос и ответ

`multipart/form-data` с файлом. Ответ — число загруженных записей и перечень ошибок по строкам. Точный контракт — после ответов на вопрос заказчику 11 и вопрос архитектору 22.
