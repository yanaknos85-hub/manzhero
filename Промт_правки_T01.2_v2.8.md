# Промт: правки T01.2 «API FavoriteRoute» v2.8 → v2.9

## Роль и задача

Ты — системный аналитик проекта «Манжерок» (АС СберТранспорт, эпик TRANSPORT-45584). Подготовь редакцию 2.9 спецификации T01.2 «API FavoriteRoute» (TRANSPORT-45586) на основе приложенной v2.8.

Внеси только изменения из этого задания. Остальной текст, структуру разделов, нумерацию D01–D26, AC и И1–И8 сохрани. Если решение затрагивает D, AC или И, обнови их статус и текст, но не перенумеровывай.

## Входные материалы

1. T01.2 v2.8 — исходный документ.
2. T01.1 «Модель данных избранных маршрутов», редакция 19.10.2026. Она дополнена таблицей `favorite_route_request` и направлена заказчику на согласование. Источник S1 обновляется на эту редакцию.
3. Стенограмма встречи с заказчиком 15.10.2026 (вопросы 31–33 = З1–З3) — при необходимости.

## Принятые решения — основания правок

Обозначения Н1–Н8 действуют только в этом задании. В v2.8 есть свои пункты Р1–Р4 (группа 1) и В1–В4 (группа 2) — не путай их с Н1–Н8.

**Н1. Граница задания (условие заказчика, формулировка 08.10, S3 §1.4).** Разрабатывается новый сервис FavoriteRoute. Существующие сервисы меняются только в двух объёмах:
- T04.1 — модель данных заявки: поля `favorite_route_id` и `favorite_route_version` в сущности, DTO, ответе чтения заявки по id и событии `service.request`;
- T01.4 и сам FavoriteRoute — только вызовы существующих методов: тарифы, договоры, geo, геозоны, corporate.

Единственная настройка вне этого объёма — маршрут `/api/favorite-routes` в gateway-main. Это зависимость от команды шлюза, а не доработка. «Пересмотр границы 08.10» больше не требуется.

**Н2. Вариант А (решение архитектора 19.10.2026): проверка заявок при деактивации — внутри FavoriteRoute.**
- T04.1 только хранит ссылку и версию маршрута и передаёт их в событии `service.request` и в ответе `GET /api/requests/{requestId}`. Новых методов и логики в сервисе заявок нет. Протокол закрытия (OPEN/CLOSED, эпоха, CloseRoute, ReopenRoute, ReadRouteClose, ReadRouteCloseBatch, HasActiveRouteRequests, служебная строка в БД заявок, восстановление CLOSED) исключается целиком.
- FavoriteRoute читает `service.request` в свою таблицу `favorite_route_request` по T01.1 ред. 19.10. Поля: `request_id` (PK), `organization_id`, `favorite_route_id`, `favorite_route_version`, `request_status`, `request_created_at`, `linked_at`, `updated_at`. Индекс по `favorite_route_id`, FK нет.
- **Обработка события.** Событие несёт полное состояние заявки.
  - Ссылка на маршрут есть — строка создаётся или обновляется (upsert).
  - Ссылки нет — строка удаляется (сброс ссылки при смене точек).
  - Событий с `deleted=true` сервис заявок не отправляет.
  - Правило «терминальный статус не перезаписывается» не применяется.
  - Неизвестный статус блокирует деактивацию.
  - Расхождение организации заявки и маршрута — техническое событие и оповещение.
- **Деактивация (DELETE).**
  1. Под блокировкой строки маршрута прочитать его связи из `favorite_route_request`.
  2. Перечитать заявки в сервисе заявок через `GET /api/requests/{requestId}` токеном пользователя. Перечитываются все незавершённые связи и ставшие терминальными за последние N часов. Окно N задаётся по задержке сообщений контрагента; сужение до отменённых — после И6.
  3. По результату обновить статус. Строку удалить, если заявки нет (404) или она больше не ссылается на этот маршрут.
  4. Связь моложе M минут при ответе 404 не удаляется: событие уходит до commit заявки, и заявка может быть ещё не записана. Такая связь считается незавершённой заявкой — 409 ACTIVE_REQUESTS_EXIST, пользователь повторяет позже (предложение по коду ошибки).
  5. Есть незавершённые — 409 ACTIVE_REQUESTS_EXIST. Неизвестный статус — 409 REQUEST_STATUS_UNCLASSIFIED.
  6. Отказ, 403 или таймаут сервиса заявок — деактивация не фиксируется (502/503/504).
- **Нестрогая гарантия.** Событие с незавершённым статусом по неактивному маршруту даёт техническое событие и оповещение. Так выявляются поздняя связь и возврат заявки из терминального статуса. Такую гарантию принимает заказчик вместе с вариантом А.
- **Флаг `hasActiveRequests`** (GET с `checkRequests=true`) считается по своей таблице, без сетевых вызовов, и может отставать. Решение о деактивации принимается только после перечитывания.
- **Чего нет.** `POST /advanced_search` не используется: он только для такси и без фильтра по маршруту и организации. Фоновой сверки и технической учётной записи нет.
- **Проверка доступности при оформлении заявки** выполняется на клиенте (T02.2/T03.2) через API FavoriteRoute токеном пользователя (S21 п. 15).
- **Зависимость.** `GET /api/requests/{requestId}` отдаёт заявку по id без фильтра по пользователю. Это фиксируется договорённостью с командой сервиса заявок. Если метод начнёт отвечать 404 на «чужие» заявки, правило удаления по 404 станет опасным. Права ролей пользователей на этот метод проверяются на стенде.
- **Условие запуска.** FavoriteRoute начинает читать `service.request` до включения автозаполнения. Подключение нового потребителя к Kafka — настройка платформы при развёртывании. Топик хранит события 7 дней.

**Н3. D20 отменено (решение архитектора 19.10.2026: таблица сотрудников не нужна).**
- Организация пользователя определяется существующим методом corporate `GET /` (через шлюз `/api/organizations/`) токеном пользователя. Для пользователя без data master метод возвращает только его организацию: id, digitId, status, organizationCode. Вызов выполняется на каждый запрос с коротким кэшем.
- Исключается: локальные проекции сотрудников, подразделений и организаций, топики `service.organization*`, gRPC All/One/Refresh, подтверждение пар employeeId/userId, первичное наполнение (resend) и readiness по проекциям.
- Недоступность corporate — 503 DEPENDENCY_UNAVAILABLE (fail-closed).

**Н4. Тариф без доработок tariff-main (решение 18.10.2026).**
- **Цена без надбавок за время (А9).** По существующей карточке тарифа (`timedTariffParams`) FavoriteRoute выбирает момент расчёта в окне записи, где временной коэффициент ровно 1,0. Окна: день 06–22, ночь 22–06. Затем вызывается существующий расчёт по `tariffId`. Нет слота с коэффициентом 1,0 — 503 CALCULATION_MODE_UNAVAILABLE. У трансфера временного множителя нет.
- **Снимок тарифа и договора** берётся из карточки. Карточка и договор читаются до и после расчёта. При расхождении — один повтор, затем 503. Риск ABA принимает аналитик.
- `favoriteRouteTransferOptions` и правило «null исключает трансфер» удаляются: по S21 п. 18 оборудование и особые условия на цену не влияют.
- Требования к tariff-main удаляются: `priceDetails`, snapshot ALWAYS, `costWithoutTimeCoefficients`. Б4 закрыт без пересмотра границы.

**Н5. Шлюз (решение 18.10.2026).** Остаётся только маршрут `/api/favorite-routes` с RewritePath для обеих форм пути. RequestSize 1 МиБ на шлюзе убирается: лимит тела в сервисе остаётся. Запрет служебных путей на шлюзе тоже убирается. Вместо него в сервисе внутренние методы закрыты сервисными ролями, а из actuator открыт только health.

**Н6. Период маршрута (З1–З3; встреча с заказчиком 15.10.2026, устно подтверждено).**
- **`validFrom` при создании** — не раньше текущей местной даты (пояс первой точки). Будущая дата допускается, например 1 января можно завести маршрут с 01.07. Прошедшая дата — 400. Сегодняшняя дата автоматически не подставляется.
- **Изменение `validFrom`.** Пока дата начала не наступила, её можно перенести на любую дату не раньше текущей — раньше или позже прежней — с соблюдением `validFrom ≤ validTo`. После наступления даты начала `validFrom` не меняется.
- Ответ 14.10 «срок можно изменять только в большую сторону» относится к `validTo`.
- **`validTo`** только увеличивается. З2 — в формулировке T01.1: «истёкшую запись, не удалённую вручную, можно продлить увеличением valid_to, если связанный тариф действует; новая запись для этого не нужна». Дополнительных условий к новой `validTo` нет. Дата проверки тарифа — как в v2.8 (местная дата сохранения). Период маршрута сроком тарифа не ограничивается.
- **З3 снят.** Истёкшие и удалённые записи не участвуют в проверке дублей. При продлении и изменении периода дубль проверяется по новому состоянию.
- **S2 исключается** («решения заказчика 15.10.2026, пункты 1–9»): первоисточника у него нет.
  - Пункты 1–4 заменяются решениями встречи 15.10. Пункты 1–2 («validFrom неизменна») неверны.
  - Пункты 5–9 есть в T01.1:
    - запрет восстановления удалённой записи;
    - истечение при чтении без фоновой задачи;
    - «Дубли и версия»;
    - 9999-12-31 и период, не ограниченный сроком тарифа;
    - отказ от автоподстановки другого тарифа.

**Н7. Факты по коду (19.10.2026) — для таблицы особенностей платформы и журнала проверки.**
- **Событие `RequestMessage`.**
  - Класс лежит в модуле messaging сервиса заявок, помечен `@JsonIgnoreProperties(ignoreUnknown = true)`.
  - Версии и времени изменения в событии нет.
  - У такси событие отправляется асинхронно внутри транзакции, до commit. Поэтому возможны «призрачные» события и потеря события.
  - `deleted=true` не отправляется.
  - Семь потребителей топика (согласования, отчёты, поездки, проверки заявок, оповещения, фрод-мониторинг, corporate) новые поля не ломают.
- **`GET /api/requests/{requestId}`** — без параметра авторизации и без фильтра по организации и пользователю. Несуществующая заявка — 404.
- **`POST /advanced_search`** — только такси. Фильтры `terminalStatus`, `creationDate` и другие; фильтра по маршруту и организации нет; токен в `taxiSearch` не передаётся. `GET /search` помечен `@Deprecated`.
- **Даты и идентификаторы.** `creationTime` — LocalDateTime в UTC. Id заявки — UUID `@GeneratedValue(AUTO)`, доступен после `save()`.
- **Обратные переходы из терминального статуса возможны.**
  - Обработчики «поездка в процессе» (`InProgressTaxiMessageProcessorImpl`, `InProgressGroupTransferMessageProcessorImpl`) меняют статус без проверки терминальности заявки.
  - `cancelSingle` при поездке в `SENT_TO_CONTRACTOR` не закрывает поездку.
  - `finish()` через `POST status/{id}/{status}` не закрывает поездку.
  - Топики `service.request.update.status` (источник в исходниках не найден) и `service.request.status.update.from.reports` (только выплаты PERSONAL/PUBLIC) меняют статус без проверок.

**Н8. Открытый вопрос к архитектору и заказчику — не принятое решение.** Остаётся ли серверная перепроверка при создании заявки (решение 08.10, А8 fail-closed)?
- По варианту А её выполняет клиент.
- Если серверную проверку оставят, T04.1 вызывает внутреннюю проверку FavoriteRoute после `save()` до commit и передаёт `requestId`. Вместе с ним передаются все обязательные поля строки, включая `request_created_at`. Вызов становится вторым источником строк `favorite_route_request` и закрывает пропущенные связи у такси и трансфера.
- Это выход за «только модель данных» сервиса заявок.
