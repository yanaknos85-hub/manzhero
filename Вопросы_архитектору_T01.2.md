## 2 Согласие с триажем v19

Проверено по исходному коду, возражений нет:

| Решение v19 | Проверка |
|---|---|
| Метод «есть ли активные заявки по `favorite_route_id`» создаётся в T04.1, а не переиспользуется | `[КОД]` Поиск слова `favorite` по исходникам сервиса заявок пуст; в DTO поиска заявок около двадцати фильтров, маршрута среди них нет |
| Права: пары «метод + URL → роль» хранит сам стартер, к сервису ролей обращаться не нужно | `[КОД]` `DatabaseRolesMigration` создаёт `urls` и `roles` **в схеме своего сервиса** (`spring.datasource.hikari.schema`, иначе имя приложения); регистрация — `PUT /allow` (`UrlEndpointAllowController`). Прежняя запись «регистрация в сервисе ролей скриптами» была ошибочной — исправлено в T01.2 v0.14 |
| Для такси проверяются признаки активности, срок договора не проверяется | `[КОД]` `CalculateServiceImpl` фильтрует только по `BaseTariff::isActive` и `Contract::isActive`; сравнения дат договора в расчёте нет. Наблюдение стенда о договорах с истёкшим сроком в статусе «Активный» этим объясняется |
| Предрасчёт остаётся методом нашего сервиса | Выбор тарифа требует цепочки геозон, а `geo-zones` доступен только по gRPC — форма такой вызов выполнить не может. Чужих контрактов метод не затрагивает |
| Ручной ввод координат: адрес определяется по координатам | `[КОД]` Обратное геокодирование у geo есть и используется: `RouteServiceImpl` вызывает `getAddressByCoordinates` для крайних координат; gRPC `getAddressCoords` задаёт `radius(10)`, REST радиус не задаёт — значение 50 м по коду не подтверждается, но механизм есть |
| 417 от geo трактуется как ошибка зависимости | `[КОД]` geo отвечает `EXPECTATION_FAILED` на любое `GeoApiException`. Но см. расхождение 2 ниже |
| Импорт не зависит от ответа заказчика | Ответы 08.10 получены: файл отклоняется целиком, перечень ошибок по строкам. Библиотека `ru.sber.transport.excel` и образец в импорте тарифов подтверждены |
| Шлюз: ни один маршрут префикс не сохраняет | `[КОД]` `gateway-main`, `application.yml`: каждое правило — `Path=/api/<ресурс>/**` с `RewritePath`, срезающим префикс. Вариант A станет первым таким правилом |

## 3 Расхождения, которые нужно закрыть самим

Архитектору их задавать не нужно, но и оставить как есть нельзя.

### Расхождение 1. Обязательность полей для `TRANSFER_CAR_CHOICE`

Приложение v19 («Решено ранее и повторно не задаётся») утверждает: «класс `TRANSFER_CAR_CHOICE`: `recommended_cost` и `tariff_id` обязательны».

В T01.1 обязателен только `tariff_id`: в таблице полей — «Да», в DDL — `tariff_id uuid NOT NULL`. У `recommended_cost` в таблице полей стоит «Нет», в DDL — `recommended_cost int4` без `NOT NULL`.

**Нужно одно из двух:** либо T01.1 правится (тогда `recommended_cost` становится `NOT NULL` и нужно решить, что писать для класса «Выбор автомобиля», где цена известна только на дату создания), либо формулировка приложения правится под модель. Второе проще и не меняет DDL.

### Расхождение 2. Код 417 и случай «адрес не найден»

Два решения приложения v19 сталкиваются:

- «417 от geo трактуется как ошибка зависимости» → наружу 502;
- «если адрес по координатам не найден, точка не принимается».

Если адрес не найден, geo отдаёт 417, а наш сервис по первому правилу превратит это в 502 «сервис недоступен». Пользователь увидит сообщение об аварии вместо «уточните точку», и исправить ввод не догадается.

`[КОД]` Внутри geo причина различается: `ControllerExceptionHandler` проверяет `GeoApiException.getCode() == 404` и пишет такой случай в лог уровнем INFO, а не ERROR. Наружу код провайдера не выводится — в теле только `message` от провайдера.

**Варианты.** **A.** Для точки без найденного адреса отдавать 422 с полем `waypoints[i]`, определяя случай по тексту сообщения geo — работает, но держится на разборе чужого текста. **B.** Попросить владельца geo различать причины: отдельный код для «адрес не найден». **C.** Оставить 502 — не рекомендуется: ввод координат руками станет непредсказуемым для пользователя.

**Рекомендация:** B как целевое, A как временное на период до изменения geo.

## 4 Остаток, не закрытый ни одним списком

**Колонки `tariff_number` в T01.1 нет.** Снятие прежнего вопроса 28 (тип и состав идентификатора тарифа) исходит из того, что человекочитаемый номер тарифа будет храниться в записи. Решение встречи 08.10.2026 это требует, но в модели поля пока нет. До его добавления обязательность `tariffNumber` в T01.2 (2.1.4, 2.6.4) опирается на решение встречи, а не на модель.

**Ожидается от заказчика:** участие класса `TRANSFER_CAR_CHOICE` в избранных маршрутах; режимы заказа «Я», «Мой коллега», «Для клиента».
